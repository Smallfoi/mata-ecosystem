# Наблюдаемость и обработка ошибок (Observability) — план и структура

Единый документ по «видимости ошибок» экосистемы МАТА: чем ловим ошибки на бэке и в
приложениях, как они попадают в одну «вкладку Ошибки», как чиним КОРЕНЬ (а не симптом),
и пошаговый план внедрения «под ключ». Решение зафиксировано в `docs/DECISIONS.md` (D-32).

> Статус: **метод утверждён, внедрение — предстоит** (владелец: «приступим в скором времени»).
> Этот файл — заготовка структуры, чтобы включение было быстрым.

---

## 1. Идея в одном абзаце

«Вкладку Ошибки» **не строим с нуля** — это зрелый класс продуктов (error tracking). Берём
готовую платформу, совместимую с Sentry-SDK, ставим её в РФ (дата-резиденция 152-ФЗ), в неё
шлют ошибки бэкенд и оба приложения. В нашей админке — только **сводка-виджет + ссылка**.
Роль «AI, чинящего корень» берёт на себя Claude.

## 2. Четыре слоя (у каждого своя задача)

| Слой | Задача | Автоматически? | Чем закрыт |
|---|---|---|---|
| Профилактика | не пустить ошибку в прод | да | тесты + CI, `check --deploy`, prodcheck |
| Устойчивость | ошибка не роняет приложение | **да** | graceful degradation, идемпотентность, офлайн-очередь, авто-restart |
| **Обнаружение** | узнать за секунды + причина | **да** | **error tracking (этот документ)** |
| Устранение | починить корень один раз | быстро, руками | Claude + тест, фиксирующий баг |

## 3. Решение: GlitchTip (self-host в РФ) — почему

- **Sentry-совместимый:** те же SDK и формат DSN → код не меняем, наш каркас заведётся сменой одной переменной.
- **Наш стек:** Django+Celery+Postgres+Redis. Работает в **512 МБ–2 ГБ** против **16 ГБ и ~40 контейнеров** у полного Sentry.
- **Дата-резиденция РФ:** ставим на наш Yandex Cloud → данные пользователей не покидают РФ (152-ФЗ, §2 LAUNCH_READINESS).
- **~80% фич:** группировка по корню, стек-трейсы, релизы, фильтры, алерты — вся нужная «видимость».
- **Минус (честно):** нет AI-Autofix (Seer есть у полного Sentry). Эту роль берёт **Claude** — разбирает топ ошибок и чинит корни каждую сессию.
- **Апгрейд-путь:** полный Sentry + Seer Autofix (авто-передача фикса в Claude Code) — позже, когда объём оправдает 16 ГБ/облако.

## 4. Что уже готово (не начинаем с нуля)

- **Бэкенд:** `sentry-sdk[django]` в requirements; init по `SENTRY_DSN` в `config/settings.py` (без ключа — no-op); статус в `check_launch_readiness`.
- **Мониторинг живости:** `/v1/health` (db+cache) и `/v1/health/ready` (200/503 для балансировщика).
- **Приложения:** `sentry_flutter` подключён и инициализирован в обоих (`main.dart`
  Квартала и Store) — ждёт только реального DSN. Осталось от этапа 3: обогащение
  контекста (release/платформа/`user_id`), breadcrumbs и деобфускация символов.

## 5. Структура вкладки «Ошибки» (что видим)

- **Шапка — release health:** crash-free users %, открытых issues, новых за 24ч, регрессий, 1–2 «горящих» (spike).
- **Список (сердце) — сгруппирован по КОРНЮ, сортировка «частота × затронуто юзеров»:**
  заголовок (тип + место) · события · юзеров · first/last seen · спарклайн-тренд · **бейдж платформы** (Квартал / Store / Сайт / Бэк) · статус.
- **Фасеты/фильтры:** платформа · версия (release) · ОС (Android/iOS/web) · устройство · окружение (prod/staging) · статус · уровень (fatal/non-fatal) · период · поиск по тексту.
- **Карточка ошибки (клик):**
  - стек-трейс (деобфусцированный) с подсветкой «виновной» строки;
  - **breadcrumbs** — что юзер делал ДО ошибки (экраны, тапы, сетевые запросы);
  - контекст: устройство, ОС, версия приложения, `user_id`; **для сетевых ошибок — endpoint, тип `DioException`, таймаут/разрыв**;
  - метрики: события, затронуто юзеров, first/last seen, тренд, версии где встречается;
  - **причина + путь фикса** (у нас: анализ Claude → правка + тест);
  - действия: назначить · resolve · ignore/mute · snooze; **авто-reopen при регрессии**.

## 6. Стадии ошибки (workflow, модель Datadog)

`For Review` (новая/регрессия) → `Reviewed` (разобрана) → `Resolved` (починена) →
`Ignored`/`Muted` (шум). Регрессия (починили, вернулось в новом релизе) — карточка **сама открывается**.

### Что именно сделано 07.09.2026

- **Вычистка ПДн** (`common/sentry_scrub.py`). `send_default_pii=False` убирает только то,
  что SDK добавляет сам; телефон в тексте исключения и токен в локальной переменной он не
  трогает. Теперь событие целиком проходит через фильтр: телефоны, почты, JWT, длинные
  ключи и номера карт заменяются на `[скрыто]`, поля вроде `password`/`authorization`
  вырезаются по имени. Тип ошибки, файл и строка остаются — разбирать причину это не мешает.
  **Фильтр не может отменить отправку:** любой сбой внутри него пропускает событие как есть,
  иначе поломка фильтра сделала бы нас слепыми. 20 тестов.
- **Крошки в приложениях.** Без них падение выглядит как «упало где-то». Теперь в карточке
  ошибки виден путь: по каким экранам шёл человек и какие запросы уходили — маршрут, метод,
  код ответа, тип сетевой ошибки. Тела, заголовки и параметры в крошки НЕ попадают.
- **Общий Dio в Квартале** (`core/api/api_client.dart`). Раньше 21 место собирало свой
  клиент — общий перехватчик пришлось бы дописывать 21 раз и один раз забыть.
- **Закрыта утечка в Store:** `ApiException.toString()` клал в текст исключения тело ответа
  целиком, а это именно то, что уезжает в трекер при непойманном исключении. Теперь наружу
  идёт только код ответа; поле `message` для показа и разбора осталось прежним.
- **Плитка на главной админки** — чтобы проблема попадалась на глаза, а не ждала, пока
  кто-то откроет трекер. Сбой трекера превращается в прочерк: дашборд важнее наблюдаемости.

## 7а. Установка на прод-сервер (D-122) — инструкция владельцу

**Где живёт:** ВРЕМЕННО на прод-ВМ Cloud.ru (решение 10.11.2026, 0 ₽). Цель — отдельная
площадка: мониторинг не должен падать вместе с магазином. Набор `backend/docker-compose.glitchtip.yml`
отдельный от прод-стека и переносится как есть.

**Что внутри:** GlitchTip 6.2.6 одним контейнером (`all_in_one`) + своя PostgreSQL 16, без
Valkey. Потолки памяти 700 + 256 МБ, на деле ~240 МБ (замер 10.11.2026). Своя база — нагрузка
от ошибок не ложится на базу магазина и не попадает в её бэкапы. Автодеплой его не трогает.
Адрес — `https://errors.mata-club.ru`, через nginx магазина: блок появляется только после
выпуска сертификата и проверки `nginx -t`; GlitchTip остановлен — магазин работает, errors
отвечает 502 (проверено).

**Порядок (вход на сервер — `ssh user1@87.242.100.147` из Cloud Shell Яндекса):**

1. **DNS у Beget:** A-запись `errors.mata-club.ru` → `87.242.100.147`.
2. `sudo bash /opt/mata/backend/deploy/glitchtip.sh setup` — проверит свободную память
   (нужно ≥ 1 ГБ) и диск, создаст секреты в `/root/mata-glitchtip.env`, базу, запустит.
   Один раз пересоздаст nginx магазина (пара секунд), чтобы он увидел каталог `nginx/extra`.
3. `sudo bash /opt/mata/backend/deploy/glitchtip.sh tls` — сертификат и адрес errors.mata-club.ru.
4. `sudo bash /opt/mata/backend/deploy/glitchtip.sh admin` — ваш вход в GlitchTip: почта и пароль.
5. `sudo bash /opt/mata/backend/deploy/glitchtip.sh connect` — проекты `backend` и `apps`, ключи,
   токен только на чтение для страницы «Ошибки» в админке; всё пишет в `/root/mata-secrets.env`
   (с копией прежней версии) и перезапускает магазин. В конце печатает DSN приложений —
   его в секрет GitHub `SENTRY_DSN`, со следующей Android-сборки ошибки телефонов тоже здесь.

Проверено локально 10.11.2026 тем же файлом и образом: миграции, вход, приём настоящей ошибки
из нашего бэкенда, показ её в `/admin/errors/` («Не решена»), повторный `connect` без дублей,
nginx с GlitchTip и без него.

**Ключи:** `connect` пишет их в файл секретов сервера, НЕ в Lockbox. При пересоздании сервера из
Lockbox их надо перенести туда (или повторить `connect`).

## 8. Ранбук устранения КОРНЯ (петля)

```
ошибка ловится в GlitchTip
  → группируется по корню (одинаковые = одна карточка + частота)
  → алерт (Telegram)
  → приоритет: частота × число затронутых юзеров
  → Claude находит и чинит КОРЕНЬ (не симптом)
  → пишет тест, фиксирующий баг → CI не даёт вернуться (регрессия закрыта)
  → деплой → проверка в трекере, что ошибка исчезла → статус Resolved
```

## 9. Конфигурация (переменные окружения)

- Бэкенд: `SENTRY_DSN` (уже есть), `SENTRY_ENVIRONMENT` (prod/staging), `SENTRY_RELEASE` (git sha), `SENTRY_TRACES_SAMPLE_RATE`.
- Приложения (Flutter): DSN через `--dart-define=SENTRY_DSN=…` в сборке; `release` берётся из версии приложения.
- Все — в `.env.example` / CI-секретах; **настоящие DSN не коммитим** (репо публичный).

## 11а. Локальный демо-инстанс (ЗАПУЩЕН — 2026-08)

Поднят локально для проверки метода до облака. **Только dev, пока включён ПК.**

- **Панель:** http://localhost:8080 · вход `admin@staw.local` / `staw-glitchtip-2026`.
- **Поднять/погасить:**
  ```bash
  docker compose -f backend/observability/docker-compose.glitchtip.yml up -d      # поднять
  docker compose -f backend/observability/docker-compose.glitchtip.yml down       # погасить (данные в томе gt-pg)
  ```
- **Как подключён наш бэк:** локальный `backend/docker-compose.override.yml` (**gitignored**) задаёт
  `SENTRY_DSN=http://<key>@host.docker.internal:8080/1` для web+worker → реальные ошибки бэка летят в GlitchTip.
  Убрать файл и пересоздать web — бэк перестанет слать (вернётся к no-op).
- **Проверено:** 3 тест-ошибки + 1 живое событие с бэка легли в панель, сгруппированы по типу (ValueError/KeyError/…).
- **Прод-отличия:** инстанс переносится на Yandex Cloud (постоянный, РФ-резиденция), DSN — в прод-`.env`, а не в override.
