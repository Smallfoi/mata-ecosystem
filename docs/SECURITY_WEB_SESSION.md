# Сессия на сайте МАТА: модель угроз и план (аудит D08)

> Статус: **документ-решение для владельца**, код сессии пока не меняли.
> Сделано в том же PR: заголовок `Content-Security-Policy-Report-Only` для сайта в
> `backend/nginx/mata.conf.example` (только наблюдение — ничего не блокирует).

## 1. Как сейчас

| Что | Где | Как |
|---|---|---|
| Токен входа | `localStorage["staw_jwt"]` | JWT HS256 `{sub, exp}`, живёт **30 дней** (`common/security.py`, `JWT_TTL`) |
| Профиль | `localStorage["staw_user"]` | JSON из ответа входа, только для отрисовки |
| Кто читает токен | `ecosystem.js`, `catalog.js`, `script.js` | заголовок `Authorization: Bearer …` на `https://api.mata-club.ru/v1` |
| Выход | `clearSession()` | стирает только локальные ключи; сам токен до истечения валиден |
| Отзыв | — | до аудита A02 не было; в PR A02 (`token_version`) появляется отзыв всех сессий при сбросе пароля/удалении аккаунта |
| CORS API | `DJANGO_CORS_ORIGINS` | только `mata-club.ru`, `www.mata-club.ru`, бакет превью |
| CSRF | не нужен | куки не используются, токен кладётся в заголовок руками |

Тот же JWT используют мобильные приложения (Квартал, Store) — там он лежит в
защищённом хранилище ОС. Контракт `Authorization: Bearer` для приложений не меняем.

## 2. Модель угроз

**Главная угроза — XSS на `mata-club.ru`.** Любой скрипт, выполненный на странице сайта,
читает `localStorage` и уносит токен. Токен живёт 30 дней и работает с любого устройства:
угонщик получает баллы, заказы, адреса и телефон владельца аккаунта.

Откуда может взяться скрипт на странице:

1. **Сторонние скрипты без SRI.** `index.html` грузит GSAP и ScrollTrigger с
   `cdnjs.cloudflare.com` и Lenis с `cdn.jsdelivr.net` без атрибута `integrity`.
   Компрометация CDN или пакета = код на нашей странице.
2. **`innerHTML` с данными.** 31 место (`script.js` 15, `catalog.js` 6, `ecosystem.js` 5,
   `legal-page.js` 3, `legal.js`, `promo.js`). Если в строку попадает текст из API
   (название товара из 1С, текст из Конструктора, имя пользователя) без экранирования —
   это хранимый XSS. Нужен отдельный проход: каждое место — `textContent` или
   экранирование.
3. **Режим правки Конструктора.** `editor.js` включается по `?edit=1` внутри любого
   iframe и принимает команды от origin из параметра `?console=`. Чужой сайт может
   встроить нашу страницу в режиме правки и управлять ею (сейчас команды пишут через
   `textContent`, прямого XSS не нашли, но доверенный origin задаёт атакующий).
   Лечится списком разрешённых origin консоли в коде и `frame-ancestors` в CSP.
4. **Расширения браузера / общий компьютер.** `localStorage` не очищается при закрытии
   браузера; токен остаётся на месяц.

Что **не** является угрозой при текущей схеме: CSRF (кук нет), кража через чужой сайт
(CORS закрыт, а токен не отправляется браузером автоматически).

## 3. Варианты

### А. httpOnly-кука + CSRF (сильнейшая защита от кражи)
- Сайт получает сессию в куке `HttpOnly; Secure; SameSite=Lax` на домене `mata-club.ru`
  (API нужно отдавать с того же сайта: `mata-club.ru/api/…` через nginx, иначе кука
  станет сторонней и Safari/ITP её режет).
- JS токен не видит → XSS не может его унести (но может действовать от имени
  пользователя, пока вкладка открыта).
- Нужны: CSRF-токен (double-submit) для изменяющих запросов, отдельная ветка
  аутентификации в `common/security.py` (кука ИЛИ Bearer), выход = удаление куки на
  сервере, проксирование `/api` в nginx сайта.
- Цена: самая большая переделка; затрагивает бэкенд, nginx и все запросы сайта.

### Б. Короткий access-токен + refresh
- Access живёт 15 минут и хранится **в памяти** страницы (не в `localStorage`);
  refresh — в httpOnly-куке (как в А) или хотя бы в `sessionStorage` с ротацией.
- Украденный access бесполезен через 15 минут; refresh ротируется и отзывается.
- Нужны: эндпоинт `/v1/auth/refresh`, хранение refresh-токенов (или их версий) в БД,
  отзыв. Хорошо сочетается с `token_version` из A02.
- Для приложений можно ввести позже тем же эндпоинтом — старые сборки продолжают
  жить с 30-дневным токеном (обратная совместимость).

### В. CSP (снижает вероятность XSS, не заменяет А/Б)
- `script-src` со списком источников, `object-src 'none'`, `base-uri 'self'`,
  `frame-ancestors 'self' https://api.mata-club.ru`, `connect-src` только на API.
- Сейчас в политике вынужденно `'unsafe-inline'` для скриптов: в `index.html` и
  `app.html` есть встроенные `<script>`. Чтобы убрать — вынести их в файлы или
  прописать sha256-хэши. Для стилей `'unsafe-inline'` останется (атрибуты `style`
  задаются из JS) — это приемлемо.
- Добавить `integrity` + `crossorigin` к трём CDN-скриптам (версии зафиксированы,
  хэш стабилен) или положить их к себе в `САЙТ МАТА/vendor/`.

### Г. Минимум без переделки
- Срок сайтового токена сократить (например, 7 дней) — отдельный параметр TTL для
  входа с сайта (поле в запросе входа или отдельный эндпоинт), приложения не трогаем.
- Серверный выход: «выйти на всех устройствах» через `token_version` (A02).

## 4. Рекомендация

1. **Сейчас (без риска):** CSP в режиме Report-Only — сделано в этом PR, ждёт
   применения на проде (см. «Как включить»). Неделю смотреть консоль браузера на
   сайте и в Конструкторе; если нарушений нет — переименовать заголовок в
   `Content-Security-Policy` (enforce).
2. **Ближайший PR сайта:** SRI на CDN-скрипты (или свои копии), список разрешённых
   origin консоли в `editor.js`, аудит 31 места `innerHTML`, вынести встроенные
   скрипты в файлы и убрать `'unsafe-inline'` из `script-src`.
3. **К публичному запуску:** вариант **Б** (короткий access в памяти + refresh в
   httpOnly-куке, выход и отзыв на сервере). Это даёт почти всю защиту варианта А без
   переделки CORS/CSRF для всего API и без поломки приложений.
4. Вариант **А** целиком — только если сайт станет основным каналом покупок и
   появится время на проксирование API через домен сайта.

## 5. Как включить CSP на проде (владельцу)

Конфиг nginx на прод-ВМ автодеплоем **фактически не обновляется** (PITFALLS «Авто-деплой
обновляет статику сайта, но НЕ конфиг nginx»). Причина, найденная при этом аудите:
`nginx/mata.conf` смонтирован в контейнер как **отдельный файл** (привязка к inode), а
автодеплой после `cp` делает `sed -i`, который подменяет файл новым (новый inode).
Контейнер остаётся привязан к старому inode: он видит конфиг таким, каким тот был на
первом автодеплое после создания контейнера, а все последующие правки уходят мимо —
`nginx -s reload` перечитывает устаревшее содержимое. (Лечение в скрипте: писать файл
на месте — `sed '…' nginx/mata.conf.example > nginx/mata.conf` вместо `cp` + `sed -i`;
скрипт автодеплоя сейчас правит отдельный PR аудита E01, поэтому здесь не трогали.)
Применить вручную на ВМ:

```sh
cd /opt/mata/backend
docker compose -f docker-compose.prod.yml --env-file .env up -d --force-recreate nginx
```

(пересоздание контейнера nginx — пара секунд без ответа сайта/API; сертификаты и
статика на томах, не теряются). Проверка: `curl -sI https://mata-club.ru | grep -i content-security`.
