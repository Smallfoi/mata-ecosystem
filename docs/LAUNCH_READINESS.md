# Готовность экосистемы к публичному запуску

Единый чек-лист инфраструктурной, юридической и операционной готовности МАТА:
«Квартал», SportStore, сайт и общий Django-бэкенд.

> Это рабочая карта рисков, а не юридическое заключение. Перед публичным запуском
> документы и процессы проверяет профильный российский юрист по IT, персональным
> данным и электронной коммерции.

> **Ревизия 15.11.2026.** Каждый пункт сверен с кодом и состоянием прода. Список
> писался до запуска бэкенда и успел устареть: больше половины «не сделано» на деле
> было сделано. Чтобы это не повторялось, у каждого закрытого пункта теперь стоит
> ДОКАЗАТЕЛЬСТВО — эндпоинт, файл или команда, которой можно проверить.
>
> Три состояния:
> - `[x]` — сделано, с доказательством в скобках;
> - `[ ] 👤` — **ждёт владельца**: реквизиты, юрист, аккаунт провайдера, касса. Кодом не закрыть;
> - `[ ]` — открыто и делается кодом/документом.

## 1. Целевая инфраструктура

> Конфигурация, цены и пошаговый порядок закупки/подключения — **`docs/YANDEX_CLOUD.md`** (D-28).

**Yandex Cloud** — предпочтительный кандидат для production всей экосистемы:

- российская инфраструктура и возможность локализовать данные пользователей;
- серверы, S3-совместимое хранилище, балансировщики, мониторинг и CDN;
- постепенный рост без обязательной смены провайдера;
- совместимость с Django, Docker, PostgreSQL/PostGIS, Redis и Celery.

**Beget не отклонён:** домен и DNS можно оставить в Beget, а backend разместить в
Yandex Cloud. Beget VPS/Cloud допустим для раннего MVP; обычный виртуальный хостинг
не соответствует нашей архитектуре и ожидаемому росту.

Перед окончательным выбором:

- [x] Сравнить стоимость облаков. *(проходили трижды: Яндекс → Beget → Cloud.ru. Прод с
  08.11.2026 на Cloud.ru, см. `docs/DEPLOY.md` и память `project-prod-deployment`.)*
- [x] Проверить версию PostgreSQL и поддержку PostGIS. *(postgis в Docker, `backend/compose.yaml`;
  территории и кварталы считаются в SQL — без PostGIS бэкенд не поднимется.)*
- [x] Проверить бэкапы и экспорт данных. *(pgBackRest в ДВА хранилища — Яндекс S3 и Timeweb S3,
  D-119; сторож бэкапов D-125 на проде; восстановление проверялось.)*
- [x] Утвердить домены API и Django Admin. *(`api.mata-club.ru`, админка на нём же `/admin/`,
  ошибки — `errors.mata-club.ru`.)*
- [x] Не создавать жёсткую зависимость от одного облака. *(проверено на практике: после сбоя
  Beget 02.11.2026 переехали целиком за неделю. Остаток зависимости — DNS и регистратор всё
  ещё у Beget, это единственная точка отказа; вынести — отдельная задача.)*

Минимальная production-схема:

```text
Квартал / SportStore / сайт
            |
        HTTPS + DNS
            |
    Nginx / reverse proxy
            |
    Django + Gunicorn
       |          |
PostgreSQL/   Redis + Celery
  PostGIS          |
       |      фоновые задачи
       |
Object Storage + CDN
```

Обязательно: HTTPS, закрытая БД, секреты вне Git, автоматические бэкапы,
проверка восстановления, мониторинг и разные dev/staging/production-окружения.

## 15. Проверка готовности и каркасы интеграций (D-30, арк 2)

**Команда:** `python manage.py check_launch_readiness` — единый отчёт: какие внешние
интеграции настроены, безопасна ли прод-конфигурация, опубликованы ли обязательные
юр-документы. Что и как включать — в `backend/django_api/.env.example` (плейсхолдеры).

**Каркасы интеграций готовы и работают как no-op в dev** — активируются переменными
окружения (провайдер + ключи аккаунта владельца), код менять не нужно:

> ⚠️ **Различай «каркас» и «реализацию».** Каркас = переключение по env есть, но
> реального вызова провайдера нет: вставишь ключи — работать НЕ начнёт. Ниже это
> указано в столбце «Реализация» честно, потому что раньше формулировка «каркас
> готов, активируется ключами» вводила в заблуждение по оплате.

| Интеграция | Флаг вкл. | Ключи (env) | Dev-поведение (без ключей) | Реализация |
|---|---|---|---|---|
| SMS-вход | `SMS_PROVIDER=smsc` | `SMS_LOGIN`, `SMS_PASSWORD` | код входа всегда `1234` | ✅ реальный вызов smsc.ru |
| Оплата | `PAYMENT_PROVIDER=yookassa` | `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_RETURN_URL` | заказ сразу «оплачено» | ✅ ЮKassa API v3: платёж, вебхук, возврат |
| Push | `PUSH_PROVIDER=rustore` | `RUSTORE_PROJECT_ID`, `RUSTORE_PUSH_KEY` | пуш — no-op (лента в приложении работает) | ✅ RuStore Push (VK PNS) + авточистка мёртвых токенов |
| Мониторинг | — | `SENTRY_DSN` | Sentry выключен |
| Кэш/очереди | — | `REDIS_URL` | LocMem-кэш + Celery EAGER (только один воркер) |
| Медиа (S3) | — | `MEDIA_S3_BUCKET`, `MEDIA_S3_ACCESS_KEY`, `MEDIA_S3_SECRET_KEY` (+ `MEDIA_S3_CUSTOM_DOMAIN` для CDN) | локальный диск `/srv/media` (D-31) |

**Доступ в админку (D-49).** Вход двухшаговый: пароль, затем код из
приложения-аутентификатора на отдельной странице `/admin/2fa/`. Работает с любого адреса —
привязку к IP (D-48) убрали, она не годится при динамическом домашнем IP.
`check_launch_readiness` показывает, у кого из суперпользователей нет второго фактора и не
остался ли пароль из известного списка.

🔑 **Владельцу — одно действие перед запуском:**

```bash
docker compose exec web python manage.py admin_2fa admin
```

Команда покажет QR (сканировать любым аутентификатором: Яндекс Ключ, Google Authenticator,
1Password) и десять одноразовых запасных кодов. **Запасные коды сохранить отдельно от
телефона** — это единственный способ войти при его потере. Новые коды — `--reset`.

**Модерация витрины платёжным сервисом.** ЮKassa включает приём платежей, только если на
сайте есть четыре вещи: настоящие товары с ценами и описаниями, информация о доставке,
оферта (или пользовательское соглашение) и контакты с реквизитами продавца. Первые три
закрыты: каталог тянется с бэкенда, «Доставка и получение» и «Возврат и обмен» добавлены как
юр-документы и выведены в подвал, оферта там же. Осталось одно — **владельцу заполнить
реквизиты** (ИП, ИНН, ОГРНИП, адрес, телефон, email) в Конструкторе: поля `footer.req.*`
стоят в подвале с прочерками. И опубликовать в прод-админке два новых документа после
проверки текста юристом (`docs/legal/09-delivery.md`, `10-returns.md`).

**Маркировка «Честного знака» — блокирует продажи, а не только оплату.** Наш мерч
попадает под обязательную маркировку: трикотаж (6101–6117), верхняя одежда (6201–6217),
обувь (6401–6405). Значит нужны: регистрация в «Честном знаке», заказ и нанесение кодов,
касса с **ФФД 1.2** и (с 01.03.2026) модулем **ТС ПИоТ**, передача кода маркировки в чеке при
продаже. Встроенные «чеки» платёжных сервисов эту задачу не закрывают: у Т-Бизнеса они прямо
запрещены для маркированных товаров, у ЮKassa сервис в тестовом режиме и про маркировку молчит.
Закладываемся на аренду облачной кассы (порядок цен и разбор — `docs/PAYMENTS_COMPARISON.md`,
раздел 4а). Это самый недооценённый пункт запуска: без него продавать одежду легально нельзя.

**Что осталось владельцу (НЕ автоматизируемо):** завести аккаунты провайдеров (smsc.ru /
эквайринг / RuStore или Firebase / Sentry), вписать ключи в прод-`.env`, поднять облако
(Yandex Cloud, D-28) с HTTPS и бэкапами, зарегистрироваться в «Честном знаке» и арендовать
кассу с ФФД 1.2, утвердить юр-пакет (§13). После вставки ключей `check_launch_readiness`
покажет соответствующие пункты как `[OK]`.
