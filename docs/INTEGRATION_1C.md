>

> только под `orderId`.

## 2. Что нужно сделать вам

Никаких эндпоинтов на вашей стороне поднимать **не нужно** — мы понимаем, что 1С
обычно стоит внутри сети и снаружи недоступна. Все запросы делает 1С, мы только

   Порядок важен, см. §4.
4. **Поставить регламентные задания** по расписанию из §9.
5. **Забирать заказы** и возвращать по ним статусы (§7).
6. **Забирать возвраты и отмены** и подтверждать приём (§7.4). 🆕
7. Ответить на вопросы из §12.

## 3. Как связываемся

| Параметр | Значение |
|---|---|
| Протокол | HTTPS |
| Метод | `POST` (выгрузки), `GET` (проверка связи, заказы) |
| Формат | JSON |
| Кодировка | UTF-8 |
| Заголовок | `Content-Type: application/json` |
| Авторизация | `Authorization: Bearer <токен>` |

**Про токен.** Один постоянный токен на все потоки. Второго фактора нет намеренно:
у робота нет телефона. Вход в админку магазина живёт отдельно и защищён иначе.
Если в настройках токен не задан, приём выключен и любой запрос получит `401` —
это нормальное поведение, а не поломка.

**Тело запроса.** Принимаем и объект, и просто массив — как вам удобнее:

```json
{ "products": [ … ] }        // именованный ключ: categories / products / prices / orders
{ "items": [ … ] }           // или обобщённый
[ … ]                        // или голый массив
```

**Ответ** на любую выгрузку — отчёт о том, что мы приняли:

```json
{ "received": 120, "created": 3, "updated": 117, "keptByOwner": ["price"], "errors": [] }
```

| Код | Что значит | Что делать |
|---|---|---|
| `200` | принято (смотрите отчёт: могут быть замечания в `errors`) | ничего |
| `400` | тело не разобрано — не JSON или не массив | проверить формат |
| `401` | токен неверный или приём выключен | взять токен у владельца |
| `413` | больше 20 000 позиций за раз | слать частями |

Позиция с ошибкой **пропускается, остальные применяются** — одна битая строка не
рушит всю выгрузку. Причина попадает в `errors` и в журнал обмена.

## 4. Поток 1 — категории

`POST /v1/integrations/1c/categories`

**Слать перед товарами.** Товар с категорией, которой у нас ещё нет, сохранится, но
не появится ни в одном разделе витрины. Такие категории мы возвращаем в
`unknownCategories` и помечаем обмен «с замечаниями» — но лучше до этого не доводить.

| Поле | Тип | Обяз. | Пример | Описание |
|---|---|:---:|---|---|
| `id` | строка | **да** | `"shoes"` или GUID | ключ категории, неизменный |
| `name` | строка | **да** | `"Кроссовки"` | название для витрины |
| `parentId` | строка | нет | `"clothes"` | родитель, если дерево |
| `sort` | число | нет | `10` | порядок отображения |

```json
{ "categories": [
  { "id": "shoes",   "name": "Кроссовки", "parentId": null, "sort": 10 },
  { "id": "tshirts", "name": "Футболки",  "parentId": null, "sort": 20 }
] }
```

Что важно знать:

- **эмодзи и фото категории — наши.** В 1С их нет, и мы их не затираем при выгрузке;
- **пропавшую из выгрузки категорию мы не удаляем** — на неё ссылаются товары, и
  удаление увело бы с витрины целый раздел. Убрать раздел — осознанное действие
  владельца в админке;
- дерево (`parentId`) мы принимаем и храним, но витрина пока плоская.

## 5. Поток 2 — карточки товаров

`POST /v1/integrations/1c/catalog` — меняется редко, отдельный поток.

**Ключ синхронизации — самое важное.** У каждой позиции нужен **неизменный**
идентификатор: GUID номенклатуры (предпочтительно) или артикул. По нему мы находим
товар и обновляем его, а не создаём второй. Идентификатор не должен меняться при
правке карточки в 1С.

| Поле | Тип | Обяз. | Пример | Описание |
|---|---|:---:|---|---|
| `id` | строка | **да** | GUID или `"SS-0042"` | ключ синхронизации |
| `article` | строка | **да** | `"AR-X1-BLK"` | артикул (SKU) |
| `name` | строка | **да** | `"Кроссовки Air Runner X1"` | наименование |
| `categoryId` | строка | **да** | `"shoes"` | ссылка на категорию из §4 |
| `brand` | строка | желат. | `"МАТА"` | бренд |
| `description` | текст | желат. | `"Лёгкие беговые…"` | описание |
| `sizes` | массив строк | да* | `["40","41","42"]` | размеры (*для обуви и одежды) |
| `colors` | массив строк | желат. | `["Чёрный","Белый"]` | цвета |
| `images` | массив URL | **не нужно** | — | фото ведёт магазин, см. ниже |
| `active` | булево | **да** | `true` | в продаже или в архиве |
| `updatedAt` | ISO дата-время | желат. | `"2026-09-01T10:00:00Z"` | для дельта-обмена |
| `weightG` | целое | желат. | `850` | вес **в упаковке**, граммы — для расчёта доставки |
| `lengthCm` | целое | желат. | `33` | длина упаковки, сантиметры |
| `widthCm` | целое | желат. | `22` | ширина упаковки, сантиметры |
| `heightCm` | целое | желат. | `12` | высота упаковки, сантиметры |
| `barcodes` 🆕 | массив строк | желат. | `["4601234567890"]` | штрихкоды этой позиции (размера и цвета) |

```json
{ "products": [{
  "id": "SS-0042",
  "article": "AR-X1",
  "name": "Кроссовки Air Runner X1",
  "categoryId": "shoes",
  "brand": "МАТА",
  "description": "Лёгкие беговые кроссовки с амортизацией.",
  "sizes": ["40", "41", "42", "43"],
  "colors": ["Чёрный", "Белый"],
  "active": true,
  "updatedAt": "2026-09-01T10:00:00Z",
  "weightG": 850,
  "lengthCm": 33,
  "widthCm": 22,
  "heightCm": 12,
  "barcodes": ["4601234567890", "2000000000017"]
}] }
```

**Штрихкоды — поле `barcodes`, массив строк.** Пришлите все штрихкоды позиции:
свой, производителя, сколько их есть. Пустые значения и повторы мы отбросим. Не
примем штрихкод длиннее 64 знаков или с пробелом внутри: такой попадёт в `errors`,
остальные штрихкоды позиции сохранятся. Поле пришло — список штрихкодов у позиции
становится ровно таким, как в выгрузке; пустой массив `[]` снимает все. Поля нет —
штрихкоды позиции не трогаем. Один штрихкод — одна позиция: если в следующей
выгрузке он придёт у другой позиции, он к ней переедет. Если в одной выгрузке он
стоит у двух позиций сразу, мы его не примем и напишем об этом в `errors`. В ответе
на выгрузку — счётчик `"barcodes": {"added": 2, "moved": 0, "removed": 0}`.

> **🆕 Добавлено 10.11.2026**
>
> **Было:** поля `barcodes` не было, штрихкоды мы не принимали (в §14 они значились
> в «этапе 2»).
>
> **Стало:** `"barcodes": ["4601234567890", "2000000000017"]` в каждой позиции.
>
> **Что сделать в 1С:** добавить поле в выгрузку карточек. Остальную выгрузку
> менять не нужно.

**Вес и габариты — в упаковке, в граммах и сантиметрах:** по ним СДЭК и Почта России
считают стоимость доставки. Если поля не пришли, мы не затираем то, что владелец ввёл
вручную, а для товаров без данных берём типовую посылку категории. Нечисловое или
нулевое значение попадёт в `errors`, остальная карточка примется.

**Фото из 1С не нужны.** Решение владельца (21.09.2026): снимки магазин готовит и
загружает сам — обмен остаётся текстовым и быстрым (пачка 3373 позиций проходит за
0,7 с; с картинками это были бы минуты и гигабайты). Поле `images` мы по-прежнему
примем, если оно у вас уже заполняется, но заводить его ради нас не нужно.

**Пустые значения можно слать смело.** `null`, пустая строка, «не указан» в `sizes`,
`colors`, `images` отбрасываются: пока карточка в 1С не заполнена, поле у нас просто не
показывается. Как заполните — значения появятся на витрине следующей выгрузкой, ничего
менять не нужно. Повторы и лишние пробелы мы тоже убираем.

**Снятие с продажи — это `active: false`,** а не удаление позиции из выгрузки.
Пропавший из выгрузки товар мы не трогаем: мало ли почему его не оказалось в пачке.

|---|---|:---:|---|---|
| `id` | строка | **да*** | `"SS-0042"` | ключ товара (*либо `article`) |
| `article` | строка | да* | `"AR-X1"` | если нет `id` |
| `price` | число | **да** | `11990` | розничная цена |
| `oldPrice` | число | нет | `13990` | старая цена, если есть скидка |
| `stock` | целое | да** | `7` | общий остаток (**либо `variants`) |
| `variants` | массив | лучше | см. ниже | остаток по размерам |

Вариант внутри `variants`: `{ "variantId": "…", "size": "41", "stock": 0 }`.

```json
{ "prices": [{
  "id": "SS-0042",
  "price": 11990,
  "oldPrice": 13990,
  "variants": [
    { "variantId": "SS-0042-40", "size": "40", "stock": 3 },
    { "variantId": "SS-0042-41", "size": "41", "stock": 0 },
    { "variantId": "SS-0042-42", "size": "42", "stock": 7 }
  ]
} ] }
```

Как мы это обрабатываем:

- **`variants` предпочтительнее.** Общий остаток мы посчитаем сами как сумму, а
  размер с нулём покупатель увидит зачёркнутым и выбрать не сможет;
- **один размер в нескольких строках** (разные цвета или склады) — складываем;
- **общий `stock` без `variants` очищает разбивку по размерам.** Это осознанно:
  старая разбивка после такой выгрузки уже неправда;
- **остаток нужен числом**, не «да/нет»;
- товар, которого у нас нет, в этом потоке **не создаётся** — придёт замечание
  «товар не найден». Сначала карточка (§5), потом цена.

**Сейчас `variants` не приходят — и это единственное, что мешает продавать.** В выгрузке на
07.10.2026 размеры у товаров есть (`sizes`), а остатка по ним нет ни у одного: приходит только
общий `stock`. Для магазина обуви и одежды это значит ровно одно — **покупатель закажет размер,
которого на складе уже нет.** Проверить размер нам нечем: при общем остатке «7 штук» мы обязаны
считать доступными все размеры карточки, иначе вообще ничего не продадим.

Отменять оплаченный заказ из-за отсутствующего размера — худшее, что магазин может сделать
покупателю, поэтому это первая по важности доработка с вашей стороны. Сам формат уже описан
выше и готов к приёму: достаточно в `variants` отдавать строку на размер с его остатком, и
размер с нулём покупатель увидит зачёркнутым и выбрать не сможет.

**Про резерв — чтобы остаток не «прыгал».** Остаток ведёте вы, мы его не пишем и не
правим. Но между оплатой и вашей выгрузкой есть окно: вещь уже продана, а в ваших
остатках ещё числится. Чтобы её не купил второй человек, мы **придерживаем её у себя**:
с момента оплаты и до тех пор, пока вы не подтвердите приём заказа (`ack`, §7.2).
Подтвердили — придержка снимается, дальше остаток ведёт ваша очередная выгрузка.

Для вас это значит одно: **подтверждайте приём заказов вовремя**. Пока `ack` не пришёл,
проданная вещь занята у нас, даже если в вашей выгрузке она ещё лежит на складе.

В позиции есть и `id`, и `article` — подставляем их из карточки товара, чтобы вам

**В очередь попадают только заказы, готовые к сборке** — оплата которых
подтверждена ЮKassa. Заказ, ожидающий оплаты, мы не отдаём: иначе у вас копятся
брошенные корзины.

**Откуда берутся деньги в заказе** (важно для документа в 1С):

| Поле | Что это |
|---|---|
| `total` | **сколько человек реально заплатил**: товары по ценам каталога **плюс** доставка **минус** списанные баллы. То же число ушло в ЮKassa и в чек предоплаты |
| `deliveryCost` | стоимость доставки, уже включена в `total`. Считает её сервер магазина по выбранному способу, а не приложение покупателя |
| `pointsRedeemed` | сколько рублей покрыто баллами лояльности. На эту сумму `total` уже уменьшен |
| `paymentId` | номер платежа ЮKassa: по нему оплату находят в личном кабинете и в поддержке ЮKassa. У тестовых заказов — `TEST-<номер>` |
| `price` в позиции | цена единицы из каталога, без учёта баллов |

То есть сумма строк плюс доставка минус `pointsRedeemed` даёт `total`. Баллы — это
скидка магазина, не оплата покупателя: в чеке они уменьшают сумму позиций.

### 7.1.1. Тестовые заказы — поле `test`

Чтобы проверить весь путь заказа, не дожидаясь подключения ЮKassa, отдельному
аккаунту выдаётся право «оплатить» без денег. Такой заказ проходит ровно тот же
путь: попадает в очередь, отдаётся вам, принимает от вас статусы. Отличие одно —
`"test": true` и номер платежа вида `TEST-<номер заказа>`.

**Настоящий заказ всегда приходит с `"test": false`.** Проводить тестовый заказ
продажей, списывать по нему остаток и печатать чек — не нужно; создайте документ,
прогоните статусы и удалите (или пометьте у себя как тестовый). Право на такую
оплату выдаёт владелец в админке одному конкретному аккаунту и снимает его после
проверки — у покупателей его нет и быть не может.

### 7.1.2. Чек: предоплату пробили мы, полный расчёт — за вами

> **✏️ Изменено 11.11.2026**
>
> **Было:** чек предоплаты пробивала касса ЮKassa, его реквизиты приходили в поле `receipt`.
>
> **Стало:** чеки ЮKassa отключены — ЮKassa только принимает деньги. **Поле `receipt`
> теперь всегда `null`.** Чек продажи с кодами маркировки пробиваете вы при отгрузке
> заказа, как в офлайн-магазине; чек возврата — тоже вы, при оформлении возврата (§7.4).
> Схема чеков ещё сверяется с бухгалтерией магазина — если изменится, предупредим здесь.
>
> **Что поменять в 1С:** не ждать реквизиты в `receipt` и не зачитывать аванс по ним.
> Текст ниже — прежняя схема, оставлен для истории.

Оплата приходит через ЮKassa, и **чек предоплаты (100%) пробивается автоматически** в момент
оплаты — сервисом «Чеки от ЮKassa». Кода маркировки в нём нет и быть не может: вещь ещё лежит
на складе, её выберут при сборке.

**При сборке заказа пробейте второй чек — «полный расчёт» с зачётом аванса**, с кодами
маркировки отсканированных вещей. Это тот же порядок, что у вас в офлайн-магазине: сканер,
списание кодов «Честного знака», чек из 1С. Без этого чека сделка останется незакрытой:
предоплата есть, передача товара не оформлена (D-101).

Немаркированные позиции (гели, аксессуары) — как обычно, без кода.

**Реквизиты чека предоплаты приходят в заказе — поле `receipt`.** Чтобы зачесть аванс во
втором чеке, нужен первый: его мы забираем из ЮKassa и кладём в заказ.

| Поле | Что это |
|---|---|
| `fiscalDocumentNumber` | номер фискального документа (ФД) |
| `fiscalStorageNumber` | номер фискального накопителя (ФН) |
| `fiscalAttribute` | фискальный признак документа (ФП) |
| `registeredAt` | когда касса зарегистрировала чек |
| `amount` | сумма чека, ₽ — по данным самого чека; совпадает с `total` заказа |
| `id` | номер чека в ЮKassa — пригодится, если придётся разбираться с поддержкой ЮKassa |

Касса пробивает чек не в момент оплаты, а через секунды или минуты после неё. Поэтому
**оплаченный заказ появляется в очереди, когда чек уже пробит**, — чтобы реквизиты пришли
сразу, а не «потом отдельно». Ждём не дольше 30 минут: если касса сломалась, заказ всё равно
уйдёт на сборку, но с `"receipt": null`. Тот же `null` — у тестовых заказов (§7.1.1, денег
не было — нет и чека). Заказ с `null` собирайте как обычно, а реквизиты чека для зачёта
аванса возьмите в личном кабинете ЮKassa по номеру заказа.

Подтверждаете по `orderIds` — номерам из выдачи. Номер, которого у нас нет,
вернётся в `unknown`. Поля `ambiguous` и `unknownServerIds` остались в ответе ради
совместимости и теперь всегда пустые.

> **Было:** `{ "serverIds": [5812] }` — так мы советовали подтверждать. Вариант
> `orderIds` считался запасным: при совпадении номеров у двух покупателей заказ
> не подтверждался и попадал в `ambiguous`.
>
> **Стало:** подтверждайте `{ "orderIds": [...] }`. Номера уникальны, `ambiguous`

### 7.3. Вернуть статус

```
POST /v1/integrations/1c/orders/status
{ "orders": [{ "orderId": "МАТА-48271593",
               "status": "shipped", "number": "УТ-000123" }] }
  → { "received": 1, "updated": 1, "errors": [], "ambiguous": [] }
```

Заказ ищем по `orderId`. Неизвестный номер ничего не меняет: он попадает в
`errors`, а строка журнала обмена получает отметку «частично».

> **✏️ Изменено 10.11.2026**
>
> **Было:** `{ "serverId": 5812, "orderId": "MATA-581431", ... }`. Заказ искали по
> `serverId`, а `orderId` был запасным путём.
>
> **Стало:** `{ "orderId": "МАТА-48271593", ... }`. Достаточно одного `orderId`.
>
> **Что поменять в 1С:** не отправлять `serverId`. Если пока отправляете, мы его
> примем, но тогда `serverId` и `orderId` должны относиться к одному заказу,
> иначе статус не применится.

| `status` | Что это | Что делает у нас |
|---|---|---|
| `accepted` | принят в 1С | покупатель видит этап, общий статус не меняется |
| `assembled` | собран | покупатель видит этап, общий статус не меняется |
| `shipped` | отгружен | заказ переходит в «Отправлен» |
| `delivered` | доставлен | заказ переходит в «Доставлен» |
| `canceled` | отменён | заказ переходит в «Отменён» |

`number` — ваш номер документа, он попадает в карточку заказа у владельца, это
сильно помогает при разборе обращений.

> **🆕 Добавлено 11.11.2026:** если заказ отменили у нас (покупатель отменил до передачи
> курьеру — §7.4), статус «Отменён» мы ставим сами. Присылать `canceled` в ответ не нужно.

По каждому статусу покупатель получает уведомление в приложении. **Один и тот же
статус, присланный повторно, ничего не меняет и второе уведомление не шлёт** —
можно спокойно перепосылать.


### 7.4. Возвраты и отмены 🆕

> **🆕 Добавлено 11.11.2026.** Раньше возвраты к вам не приходили.

Покупатель оформляет заявку на возврат в приложении или на сайте, магазин осматривает
вещи и решает по каждой. Когда деньги покупателю **уже вернулись** (это подтверждает
ЮKassa), возврат попадает в очередь для вас. Туда же — **отмена заказа**, если покупатель
отменил его до передачи курьеру. Решение принимает магазин, вам — оформить документы.

```
GET /v1/integrations/1c/returns?limit=200
```

```json
{ "returns": [{
  "returnId": "МАТА-48271593-В1",
  "type": "return",
  "orderId": "МАТА-48271593",
  "orderDocument": "УТ-000123",
  "createdAt": "2026-11-12T09:15:02+00:00",
  "customer": { "phone": "+79148278470", "name": "Михаил", "email": "m@example.com" },
  "items": [
    { "id": "GUID-2", "article": "TS-1", "barcodes": ["4601234567891"], "productId": "p2",
      "name": "Футболка", "size": "M", "color": "Белый",
      "qty": 2, "price": 1000, "refund": 2000,
      "reason": "size", "reasonLabel": "Не подошёл размер" }
  ],
  "deliveryRefund": 0,
  "amount": 2000,
  "pointsReturned": 0,
  "pointsRevoked": 100,
  "refundId": "2f6c0a1e-0015-5000-8000-1c2d3e4f5a6b",
  "test": false
}] }
```

| Поле | Что это |
|---|---|
| `returnId` | **номер возврата**: номер заказа + `-В` + порядковый номер возврата по этому заказу. Уникален. Под этим же номером покупатель видит свою заявку |
| `type` | `return` — вещи были у покупателя и вернулись; `cancel` — заказ отменён до передачи курьеру |
| `orderId` | заказ, к которому возврат (тот, что вы получили в §7.1) |
| `orderDocument` | ваш номер документа заказа, если вы присылали его в статусе (§7.3) |
| `items` | что вернули: позиция определяется по `id` и `article`, как в заказе. Одинаковые вещи — одной строкой с `qty` |
| `price` | цена единицы из каталога, без баллов |
| `refund` | сколько денег вернули за строку: из суммы оплаты, со скидкой баллами, разложенной по позициям |
| `reason`, `reasonLabel` | причина покупателя (`size`, `style`, `defect`, `not_as_described`, `wrong_item`, `other`); пусто, если возврат оформлен в магазине без заявки |
| `deliveryRefund` | сколько вернули за доставку: доставка возвращается вместе с последней вещью заказа |
| `amount` | всего вернули деньгами = сумма `refund` + `deliveryRefund` |
| `pointsReturned` / `pointsRevoked` | баллы лояльности: вернули покупателю / сняли начисленные за заказ. Для справки — баллы ведёт МАТА |
| `refundId` | номер возврата в ЮKassa: по нему возврат находят в личном кабинете ЮKassa |
| `test` | `true` — тестовый заказ (§7.1.1): денег не было, продажей не считать |

**Что делать в 1С:**

| `type` | Что произошло | Что сделать |
|---|---|---|
| `return` | вещи у магазина, деньги покупателю вернули | документ возврата к заказу `orderId`; **чек возврата на кассе** на сумму `amount`; коды «Честного знака» — в оборот; вещи — на склад |
| `cancel` | заказ отменили до передачи курьеру | отменить документ заказа, снять резерв; **чек не нужен** — товар со склада не уходил, чек продажи не пробивался |

В очередь попадают **только проведённые возвраты** (ЮKassa подтвердила, что деньги
ушли) и **только по заказам, которые вы забирали**. Если заказ отменили раньше, чем
1С его забрала, — к вам не придёт ни заказ, ни отмена: отменять у вас нечего.

**Подтвердить приём — обязательно:**

```
POST /v1/integrations/1c/returns/ack
{ "returnIds": ["МАТА-48271593-В1"],
  "documents": { "МАТА-48271593-В1": "ВЗ-000045" } }
  → { "acked": 1, "unknown": [] }
```

`documents` — по желанию: ваш номер документа возврата, он появится в карточке
заказа у владельца. Возврат остаётся в очереди, пока не придёт подтверждение;
повторное подтверждение ошибкой не считается. Неизвестный номер вернётся в `unknown`.

**Покупатель просит отменить заказ, который вы уже собираете.** Это не приходит к
вам запросом: сотрудник магазина получает письмо, проверяет, что заказ не передан
курьеру, и подтверждает отмену в админке. После этого отмена придёт в очередь с
`"type": "cancel"`. Если заказ уже у курьера — отмену отклоняют, покупатель оформит
возврат после получения.

## 8. Право вето владельца — почему цена может «не примениться»

Шесть полей владелец магазина может вести вручную: **цена, старая цена, описание,
размеры, цвета, фото**. Если он поправил поле в конструкторе витрины, следующая
выгрузка это поле **не перезаписывает** — оно приходит в отчёте в `keptByOwner`.
Значение из 1С мы всё равно сохраняем и показываем владельцу рядом, у него есть
кнопка «вернуть как в 1С».

Это не ошибка обмена. Если видите поле в `keptByOwner` — значит владелец сознательно
ведёт его сам.

**Остаток — исключение: он всегда берётся из 1С** и переопределению не подлежит.
Показать размер, которого нет на складе, дороже любого удобства.

## 11.1. Что мы видим на своей стороне

На каждый ваш запрос ответ содержит два поля для самопроверки:

- `unknownKeys` — имена полей, которые вы прислали, а мы не читаем. Если поле есть
  здесь, значит в карточку оно не попало: либо название другое, либо его нет в §5.
- `sample` — одна ваша позиция так, как мы её получили (самая полная из пачки,
  строки обрезаны до 200 символов).
- `fields` — по каждому полю: у скольких позиций оно **непустое**, например
  `"categoryId": {"filled": 214, "of": 3373, "known": true}`. Поля с `known: false`
  мы не читаем. Пустая строка, `null` и список из пустот считаются незаполненными.

Смотрим **всю пачку**, а не начало: новое поле в 1С сначала заполняют у нескольких
карточек, и они запросто оказываются в конце выгрузки.

То же самое видно владельцу в админке: «Мониторинг» → «Обмен с 1С» → колонка
«Подробности»: строка «1С прислала, а мы не читаем: …» и раскрывающийся «Пример
присланной позиции». Это снимает спор «мы присылаем» — «а мы не видим»: видно пакет.

## 13. Три склада — что нам нужно от вас

Магазин планирует работать с **тремя складами** и показывать покупателю общий остаток
по всем трём сразу. Покупатель видит только размеры — на каком складе что лежит, ему
знать не нужно. Заказ при этом должен раскладываться по складам: если из шести пар две лежат
на первом складе, две на втором и две на третьем — уходит три заказа, по одному на склад.
Если весь заказ собирается с одного склада — уходит один.

Прежде чем это делать, нужны ответы на два вопроса. **От первого зависит примерно
половина объёма работы.**

### Вопрос 1. Кто присылает остатки

Если склады — узлы одной распределённой базы, то у центрального узла уже есть остатки
всех трёх. Тогда возможны два устройства обмена, и первое для нас заметно лучше:

| | Вариант А — шлёт центральный узел | Вариант Б — каждый склад шлёт сам |
|---|---|---|
| Выгрузок | одна, как сейчас | три независимых |
| Токенов | один, как сейчас | по одному на склад |
| Картина остатка | целостная | приходит частями |
| Гонки при одновременной отправке | нет | нужна отдельная защита |

**Вопрос: умеет ли ваша конфигурация отдавать сводный остаток с разбивкой по складам
из центрального узла?** Если да — берём вариант А, и для вас это правка одной выгрузки,
а не трёх новых.

### Вопрос 2. Кто забирает заказы

Забор заказов у нас уже работает (§7): 1С сама приходит за ними и подтверждает приём.
Для трёх складов нужно понять: **каждый склад будет ходить за своей частью заказа
отдельно, или центральный узел заберёт заказ целиком и разложит его внутри 1С сам?**

Оба варианта нам подходят. Во втором случае мы всё равно пришлём разбивку по складам
внутри заказа — чтобы вам не пришлось считать её заново.

### Что меняется в формате остатков

Одно новое поле в строке варианта — код склада:

```json
{ "prices": [{
  "id": "SS-0042",
  "price": 11990,
  "variants": [
    { "size": "41", "stock": 2, "warehouse": "msk-1" },
    { "size": "41", "stock": 3, "warehouse": "msk-2" },
    { "size": "42", "stock": 7, "warehouse": "spb-1" }
  ]
} ] }
```

Код склада — любая строка, лишь бы она **не менялась со временем**: `msk-1`, `sklad-3`,
GUID склада из вашей базы. Пришлите список кодов с человеческими названиями, мы заведём
их у себя один раз.

Обратная совместимость в обе стороны. **Если поля `warehouse` нет, позиция считается
основным складом** — сегодняшняя выгрузка продолжит работать без единой правки. И наоборот:
**поле можно начинать присылать сразу, не дожидаясь нас.** Приём уже складывает несколько
строк одного размера в один остаток, поэтому покупатель увидит верное число ещё до того,
как мы заведём склады у себя; сам код склада мы сохраняем и начнём использовать для
раскладки заказа, когда получим ответы на два вопроса выше.

### Присылайте остаток, а не изменение остатка

Это важно, и на этом обычно спотыкаются. Нам нужно **«на складе msk-1 размера 41 сейчас
две пары»**, а не «со склада msk-1 убыло две пары».

Разница в том, что происходит при сбое:

| Что случилось | «Убыло 2» | «Сейчас 2» |
|---|---|---|
| Сообщение не дошло | остаток неверный навсегда | следующая выгрузка исправит сама |
| Сообщение ушло дважды | списали вчетверо | записали то же число, ничего не произошло |
| Сообщения пришли не по порядку | остаток разъезжается | побеждает свежее |
| Кладовщик поправил вручную | мы не узнаем | узнаем на следующей выгрузке |

Обмен «сколько есть» сам себя чинит: любое расхождение живёт до следующей выгрузки.
Обмен «на сколько изменилось» требует, чтобы **ни одно** сообщение никогда не потерялось —
такой гарантии не даёт ни один канал связи.

На вашем сценарии это ничего не усложняет: после перемещения склад-отправитель шлёт свой
новый остаток, склад-получатель — свой, просто каждый говорит «у меня теперь столько».

### Чего от вас НЕ требуется

- считать общий остаток по складам — сложим сами;
- решать, с какого склада брать товар в заказ — разложим сами;
- присылать движения и перемещения между складами — нам нужен только итог.
