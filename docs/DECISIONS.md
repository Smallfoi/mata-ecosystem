# DECISIONS — принятые решения по экосистеме МАТА

Короткие записи о принятых решениях и их причинах, чтобы Claude и Codex не
переобсуждали одно и то же. Менять решение можно — но с новой записью и причиной.

Формат: `## D-NN — заголовок` + Контекст / Решение / Причина / Статус.

## D-70 — «Лига» стала Кварталом: одно боевое приложение
**Решение:** dev-приложение «ЛИГА» (`mata_liga/`, D-59) 05.09.2026 целиком заменило
боевой Квартал: код перенесён в `mata_kvartal/` с идентичностью Квартала
(`ru.mata.kvartal`, пакет `kvartal_app`, имя «КВАРТАЛ», канал `app/kvartal`),
старый код Квартала удалён, CI-job `liga-app` снят. «Лига» была ВРЕМЕННЫМ именем
только для различия версий; вкладка «Лига» внутри приложения (дивизионы, зачёты)
остаётся — это название игровой механики. Обновление тестерам встаёт поверх
(та же подпись и applicationId, ключи хранилища `kvartal.*` совпадают);
minSdk вырос до 26 (Android 8.0, требование Health Connect).
**Причина:** параллельная жизнь двух приложений выполнила свою задачу (Квартал 2.0
обкатан локально), дальше она только дробит внимание и тестовую базу.
**Статус:** активно.

## D-69 — Вторым фактором человек управляет сам, но только подтвердив, что он — это он

**Контекст:** после D-68 второй фактор стал обязательным, но управлять им было негде.
На странице настроек аккаунта менялись почта, имя и пароль, а фактор не показывался вовсе:
не видно, подключён ли он, сколько осталось запасных кодов, и нечем сменить телефон.
Замечание владельца: «в GitHub такая функция есть, а у нас почему-то нет».

**Решение:** страница `/admin/account/security/` — статус фактора, имя устройства, остаток
запасных кодов; действия «сменить устройство» и «перевыпустить запасные коды». Кнопка на
страницу стоит рядом со сменой пароля: пароль и фактор — одна тема «как я вхожу», искать
их в разных местах человек не должен.

**Три правила, без которых функция была бы опаснее её отсутствия:**
1. **Каждое действие требует текущего кода** — из приложения или запасного. Одной
   пройденной при входе проверки мало: сессию могли перехватить уже ПОСЛЕ входа, и смена
   устройства без подтверждения означала бы, что чужой перепривязывает фактор на свой
   телефон и запирает владельца навсегда. Так же поступает GitHub.
2. **Страница лежит ВНЕ префикса `/admin/2fa/`.** Тот префикс намеренно пропускает мимо
   проверки кода — иначе нельзя было бы привязать первое устройство. Управлять фактором
   вправе только тот, кто фактор уже прошёл, поэтому адрес другой: `/admin/account/security/`.
3. **Отключить фактор нельзя** — он обязателен (D-68). «Сменить устройство» снимает старое
   и сразу ведёт на привязку нового; безфакторного состояния между шагами не возникает,
   потому что middleware в него и не пустит.

Потерян и телефон, и запасные коды — страница не поможет намеренно. Восстановление только
с сервера: `manage.py admin_2fa <логин> --reset`.

**Причина:** обязательный фактор без самообслуживания превращает смену телефона в обращение
к разработчику. Но самообслуживание без подтверждения превращает угон сессии в захват учётной
записи навсегда. Нужны обе половины сразу.

**Статус:** активно.

## D-68 — Второй фактор обязателен для всех, включая владельца; вход укреплён и проверен на взлом

**Контекст:** директива владельца — двухфакторная защита у ВСЕХ, у кого есть доступ в
админку, вход защитить максимально, затем попытаться сломать. Аудит показал главную дыру:
второй фактор спрашивали только у того, кто УЖЕ привязал устройство. На проде это значило,
что у сотрудника 2FA есть, а у владельца (самой ценной учётки) — нет: вход по одному паролю.

**Сделано:**
1. **Второй фактор обязателен без исключений.** Нет устройства — не в админку, а на страницу
   привязки. Послабление «без устройства пускаем как раньше» снято. Запереться нельзя:
   страница привязки открыта, потерян телефон — запасные коды, потеряны и они —
   `manage.py admin_2fa <логин> --reset` с сервера.
2. **Закрыт открытый редирект** на странице кода: `?next=` пускал только на свой домен
   (было — на любой, идеальная фишинг-приманка на нашей же ссылке).
3. **Анти-брутфорс теперь в двух разрезах:** по IP И по логину. Только по IP перебор одной
   учётки с меняющихся адресов (ботнет, список прокси) не ловился, а логин владельца
   предсказуем.
4. **Экспоненциальная пауза между кодами** (django-otp throttle) + общий по человеку лимит
   на попытки кода: с двумя устройствами (приложение + запасные коды) было два бюджета.
5. **Смена ключа сессии после второго фактора** (защита от фиксации), промах по коду пишется
   в журнал доступов, куки `SameSite=Lax` + `HttpOnly`, `Referrer-Policy: same-origin`.

**Проверка на взлом:** 21 регресс-тест атак (`common/tests_security.py`) + живой пентест по
HTTP — 11/11 отбито: JWT alg=none, битый/просроченный/чужой токен, обход 2FA адресом и
подменой чужого устройства в сессию, открытый редирект, перебор кода и логина, эскалация
сотрудника через форму, приём 1С без токена, утечка трейсбеков. Инфраструктура прода: Django
наружу не торчит (только 80/443 через nginx — `X-Real-IP` не подделать), SSH только по ключам.

**Причина:** вход в админку — единственная дверь к деньгам, ПДн и публикации; за ней же
вкладка выдачи прав. Одного пароля мало, а найденная дыра держала владельца именно на нём.

**Статус:** активно. На проде владельцу привязать устройство при первом входе после выката.

## D-67 — Палитра САЙТА: вариант Б; Store остаётся на брендбуке mudreza

**Контекст:** палитра держалась «по факту кода», без утверждённого источника. Собрал три
варианта и показал владельцу живьём, образцами: **А** — палитра mudreza (`#f1f1ef` / `#1a1e1b` /
`#eeea83`, Roboto Serif + Inter); **Б** — та, на которой живёт сайт (`#f4f1ea` / `#111317` /
голубой `#57bcd8` / лайм `#dff45f`, Unbounded + Manrope); **В** — гибрид (нейтрали mudreza +
голубой акцент). Рекомендовал В.

**Решение владельца (2026-09-02):**
1. **Сайт — вариант Б.** Эталон: `docs/DESIGN.md` (до этого решения файл сознательно не
   коммитился — он описывает именно Б, и закреплять его до выбора было нельзя).
2. **`mata_store` не перекрашиваем.** Магазин на палитре брендбука mudreza (D-34): графит
   `#2a302c`, лайм `#eeea83`, лавандовый `#b6b7bf`, Inter. Он работает и совпадает с
   айдентикой; палитра приложения решается отдельно, отдельным решением.
3. Как следствие — **область `DESIGN.md` сужена до сайта**. Сайт и магазин сейчас выглядят
   по-разному, и это осознанный выбор, а не рассинхрон.

**Причина:** «оставляем Б» — это в первую очередь про то, что перекрашивать ничего не надо.
Сайт уже на Б, менять нечего; магазин трогать не за чем — он живой и брендовый.

**Важная поправка к дизайн-проекту:** в артефакте у варианта В в минусах стояло «переделка
сайта и Store — работа, которой в варианте Б нет». Для сайта это верно, для Store — нет:
магазин никогда не был на Б, он на mudreza (32 файла из 69 используют её токены). Ошибка
моя, обнаружена при закреплении решения; артефакт исправлен.

**Статус:** активно. Дизайн-проект с образцами:
https://claude.ai/code/artifact/6cc46e19-5c69-4659-8ff2-be3515ad7035

## D-66 — Помеченный забег держится до решения человека, баллы гасятся встречной записью

**Контекст:** анти-чит (S-04) умел ставить забегу флаг и не платить за него, но дальше
следовала тишина. Модератору был доступен только плоский список забегов — видно строку,
не видно человека: сколько у него флагов, честны ли остальные забеги, нет ли рядом второго
аккаунта с того же телефона. Бегун же не узнавал ничего: забег на месте, баллов нет,
выглядит как поломка приложения.

**Решение:**
1. **Флаг — это пауза, а не приговор.** Помеченный забег ждёт решения человека на странице
   «Проверка забегов» (`/admin/runs-review/`, вкладка «Забеги»). Автоматических банов нет.
2. **Решение принимают, глядя на бегуна целиком:** карточка с его цифрами (чистые забеги,
   засчитанные км, флаги за неделю, баланс), признаки мульти-аккаунта и все его помеченные
   забеги рядом.
3. **Баллы не переписываем задним числом.** Ошибочное начисление гасится встречной
   транзакцией `runnerRunRevoked`, а не удалением записи: история баллов обязана сходиться,
   даже когда ошиблись мы. По той же причине «пересчёт» только доначисляет недостающее
   и корректирует лишнее новыми строками.
4. **Решение не стирает улику.** Признанный нарушением забег остаётся помеченным, с причиной;
   меняется только отметка «разобран», кем и когда.
5. **Мульти-аккаунт ищем по фактам, а не по догадкам:** общее устройство (история пар
   «устройство + аккаунт», модель `DeviceAccount`) и общий телефон. Это подсказка модератору —
   телефоном делятся с близкими, номера меняют, поэтому решение всегда за человеком.
6. **Уровни вкладки разведены по тяжести:** «смотреть» — читать очередь; «редактировать» —
   решения по забегам, пересчёт, снять метку; «редактировать и удалять» — блокировка аккаунта.
   Блокировка вдобавок требует вкладки «Пользователи»: она отрезает человеку вход, то есть
   это действие над учётной записью, а не над забегом. Иначе модератор бега получал бы
   власть над людьми в обход выданных вкладок (D-63).
7. **Бегун получает объяснение:** «Забег на проверке» (не чаще раза в сутки, без обвинений),
   затем «Забег подтверждён, +N баллов» либо «Забег не засчитан».

**Причина:** придержанные баллы — это деньги пользователя. Их нельзя ни потерять молча, ни
списать без следа, ни отдать по одному клику без контекста о человеке.

**Статус:** активно.

## D-65 — Система наград Квартала «Штамп МАТА»

**Решение:** награды Квартала строятся на одном шестигранном штампе (форма квартала карты):
кант кодирует категорию, металл — ранг (сталь→бронза→серебро→золото→иридий), эмблема —
награду; эмаль только у иридия и отдельных лимитированных. Медали именные: реверс с личной
гравировкой (пик/время/дата/город из GPS), лимитированные чеканятся заново каждый год.
Обязательные правила: без наложений (геометрией), надписи только по круговым дугам, фон
поля — азурирование без лучей, эмблемы — иллюстрации (не пиктограммы), цифры на плашках,
у каждой медали своя анимация эмблемы. Эталон: `docs/design/medals/shtamp-mata.html`.
**Причина:** утверждено владельцем 2026-09-01 после 9 итераций; серия-2027 строится на
этом же штампе. Это осознанное исключение из D-01 (дизайн не трогаем) — по прямой директиве.
**Статус:** активно; в приложение не внедрено.

## D-64 — Суперпользователь один и закреплён по идентификатору записи

**Контекст:** в админке оставалась галочка «суперпользователь» — то есть способ одним
кликом обойти всю систему доступов (D-63). Требование владельца: «суперпользователь —
только я, независимо от того, какую почту и пароль я себе поставлю и откуда войду».

**Решение:**
1. **Закрепляем идентификатор записи, а не почту и не логин.** Почта, логин, пароль и имя
   меняются — идентификатор выдаётся один раз и не меняется никогда. Устройство и адрес
   входа роли не играют вовсе: права привязаны к записи, а не к сессии или браузеру.
2. **Где хранится закрепление**, по убыванию силы: переменная окружения `MATA_OWNER_ID` →
   строка `OwnerPin` в базе (ставится автоматически по первому суперпользователю и живёт
   вместе с базой) → если суперпользователей нет вовсе, ничего не принуждаем.
3. **Правило держится непрерывно**, а не при сохранении формы: сигнал на сохранение
   учётной записи и проверка на каждом запросе. Любая другая запись теряет флаг, владелец —
   получает обратно. Владельца нельзя ни разжаловать, ни отключить, ни лишить входа в
   админку: иначе одним неверным сохранением он запирает себя снаружи.
4. **Из админки суперпользователем не стать:** блок «Права доступа» (`is_superuser`,
   `is_staff`, группы, права) убран из формы целиком, создание учётных записей там закрыто.
   Сотрудники заводятся только во вкладке «Сотрудники».
5. **Сменить владельца можно только с сервера:** `manage.py mata_owner --set <id>`.
   Закрепление намеренно не редактируется из интерфейса — иначе «единственный владелец»
   переписывался бы там же, где его и защищают.
6. `createsuperuser` больше не создаёт второго владельца: флаг снимается сразу.

**Причина:** любая галочка «сделать суперпользователем» в интерфейсе обесценивает систему
прав целиком — она превращает многоуровневый доступ в один клик. Владелец должен быть
свойством системы, а не полем формы.

**Статус:** в бою с 2026-09-01. На проде закреплён id=1 (`admin`).

## D-63 — Доступы сотрудников: право выдаётся на вкладку, раздавать его может только владелец

**Контекст:** в админку нужен доступ не только владельцу. При этом кастомные страницы
(Конструктор, Журнал обмена, Ошибки, Диски) были открыты ЛЮБОМУ пользователю с `is_staff` —
достаточно было прямой ссылки.

**Решение:**
1. **Единица права — вкладка меню, а не модель.** Реестр вкладок — `staff/tabs.py`; одна
   вкладка может закрывать несколько моделей (например «Клубы» — клубы, участники, заявки,
   челленджи). Владелец мыслит разделами меню, а не таблицами базы.
2. **Четыре уровня:** нет доступа / смотреть / редактировать / редактировать и удалять.
   Удаление — отдельная ступень: большинству сотрудников оно не нужно, а стереть заказ
   насовсем можно один раз.
3. **Права Django выводятся из вкладок** через `staff.backends.TabPermissionBackend`.
   Не правим два десятка ModelAdmin — любой забытый класс стал бы дырой; вместо этого
   встраиваемся в `user.has_perm()`, которым Django сам гейтит списки, кнопки и действия.
   Кастомные страницы закрыты декоратором `@tab_required(key, level)`.
4. **Вкладка «Сотрудники» — только суперпользователю**, и не пунктом меню, а на сервере
   (`@superuser_required`). Этим правом нельзя поделиться: его нет в реестре вкладок.
   Сотрудника-суперпользователя интерфейс менять отказывается — только консоль сервера.
5. **Приглашение вместо выдачи пароля.** Владелец заводит сотрудника и получает одноразовую
   ссылку на 48 часов; пароль человек задаёт себе сам. В базе хранится только отпечаток
   токена (sha256), сравнение — за постоянное время, попытки подбора ограничены.
   Когда появится почтовый сервис, письмо начнёт уходить само — переделывать нечего.
6. **Второй фактор обязателен для сотрудников.** У владельца он подключается командой
   (D-49) и остаётся его выбором; сотруднику такой возможности нет, поэтому админка не
   открывается, пока телефон не привязан. Страницу входа это не трогает.
7. **Журнал доступов**: кто, кому, что изменил и с какого адреса — стирать из интерфейса нельзя.

**Про подстановку чужого id.** Кого меняем — берётся из адреса, но право менять проверяется
по сессии: страница сначала требует владельца и только потом читает id. Уровень доступа
считается по текущему пользователю, а не по параметрам запроса, поэтому подмена id в ссылке
или поля в форме ничего не даёт. Это закреплено тестами (`staff/tests.py`).

**Причина:** «сотрудник видит всё, потому что is_staff» — самый частый способ потерять
контроль над админкой. Право должно быть явным, видимым в одном месте и проверяться на
сервере, а не прятаться в меню.

**Статус:** в бою с 2026-09-01. Пароли сотрудников проверяются строгими правилами
(10+ знаков, не словарный, не похож на почту) — заданы локально для приглашения,
общий вход не тронут.

## D-62 — Обмен с 1С: 1С — источник правды, Конструктор — право вето владельца

**Контекст:** номенклатура, цены и остатки ведутся в 1С. Но владелец хочет точечно
править витрину (акционная цена, свой текст) — и чтобы следующая выгрузка это не стёрла.

**Решение:**
1. 1С шлёт данные сама, по HTTPS: `POST /v1/integrations/1c/catalog` (карточки) и
   `POST /v1/integrations/1c/prices` (цены и остатки), проверка связи — `GET .../1c/status`.
   Авторизация — постоянный `Authorization: Bearer <токен>`, без второго фактора: у робота
   нет телефона, а вход в админку живёт отдельно и остаётся с 2FA (D-49).
2. **Гибрид.** Импорт обновляет поле, только если владелец его не трогал. Пришедшее из 1С
   всегда сохраняется в `Product.from_1c`, ручные поля перечислены в `Product.overrides`.
3. **Без переключателя режима.** Правка поля в Конструкторе = «веду сам»; возврат к значению
   1С (кнопка «вернуть как в 1С») снимает признак, и обновления снова приходят автоматически.
4. **Остаток переопределять нельзя** — он всегда из 1С. Показать размер, которого нет
   на складе, дороже, чем неудобство от жёсткого правила.
5. **Журнал обмена** — вкладка в блоке «Мониторинг» админки: дата, операция, статус,
   сколько получено / добавлено / обновлено, замечания. Хранится 90 дней.

**Причина:** учёт должен оставаться в 1С — двойной ввод неизбежно расходится. Но витрина
живёт быстрее учёта, и владельцу нужна возможность поменять цену к акции, не заводя её
в 1С. Правило «ручное побеждает, пока владелец сам не отказался» разрешает конфликт
предсказуемо и не требует от него держать в голове режимы полей.

**Статус:** в бою с 2026-08-31 (приём), Конструктор и журнал — с этой же даты.
Токен продублирован в Lockbox (`mata-prod-secrets` → `INTEGRATION_1C_TOKEN`), чтобы
пережить пересоздание ВМ.

**Дополнение 02.09.2026 — категории и остаток по размерам.**

4. **Категории принимаются отдельным потоком** (`POST /1c/categories`), порядок при
   первой выгрузке: категории → каталог → цены. Раньше эндпоинта не было вовсе, и
   товар с незнакомой категорией сохранялся молча — `category_id` у нас строка, а не
   внешний ключ, поэтому ошибки не возникало, но товар пропадал из разделов витрины.
   Теперь такие категории возвращаются в `unknownCategories` и делают обмен
   «с замечаниями» в журнале. Молчать об этом хуже, чем показать замечание.
5. **Категории, пропавшие из выгрузки, не удаляем.** На категорию ссылаются товары,
   и молчаливое удаление увело бы их с витрины целым разделом. Убрать категорию
   осознанно проще в админке, чем потом разбираться, куда делся раздел.
6. **Эмодзи и фото категории — наши.** В 1С их нет, и затирать пустотой при каждой
   выгрузке нельзя. 1С ведёт только название, порядок и родителя.
7. **Остаток по размерам доведён до витрины.** `variants[{size, stock}]` раскладывается
   в `stockBySize`, общий остаток — сумма. Размер без остатка на витрине показан, но
   зачёркнут и не выбирается: спрятать его — значит заставить человека гадать, был ли
   его размер вообще. Общий `stock` без вариантов очищает разбивку — она уже неправда.

**Дополнение 02.09.2026 (вечер) — заказы в 1С и пакетная запись.**

8. **Заказы забирает 1С, а не мы отправляем.** Её сервер обычно за NAT, достучаться
   снаружи нельзя. Направление обмена одно и то же во всех потоках: 1С приходит к нам.
9. **Выдача и подтверждение — разные запросы.** Заказ уходит из очереди только после
   `ack`, когда документ у 1С уже создан. Оборванная связь тогда стоит одного лишнего
   запроса, а не потерянного заказа. Отдавать и сразу забывать нельзя: это деньги
   покупателя. Повторный `ack` — не ошибка.
10. **В 1С уходят только заказы, готовые к сборке** (оплата не требуется или прошла).
    Заказ, ждущий оплаты, не выдаётся: иначе на складе копятся брошенные корзины и
    кладовщик собирает то, за что никто не заплатил.
11. **Этапы склада не двигают статус заказа.** `shipped`/`delivered`/`canceled` меняют
    общий статус; `accepted` и `assembled` — внутренняя кухня 1С: покупатель видит их
    отдельной строкой и получает уведомление, но общий статус остаётся прежним.
12. **Пакетная запись вместо построчной.** Раньше на каждую позицию уходило по
    несколько обращений к базе, и выгрузка в тысячу товаров упиралась в таймаут.
    Теперь всё, что уже есть, читается одним запросом, а запись идёт пачками по 500.
    Число обращений к базе не зависит от числа позиций — это зафиксировано тестом,
    иначе оно тихо вернётся при первой же правке. Потолок на запрос — 20 000 позиций,
    дальше 413 с просьбой прислать частями.

## D-61 — «Лига» живёт локально и в бой не выкатывается

**Решение:** `mata_liga/` — тестовое приложение. На телефон ставится ТОЛЬКО debug-сборка,
которая ходит на локальный backend (`http://127.0.0.1:8000/v1` + `adb reverse tcp:8000 tcp:8000`).
Release-сборка «Лиги», смотрящая на прод, на телефон не ставится и никому не раздаётся.
Боевое приложение — «Квартал»: release, прод, обновления тестировщикам.

**Что где разрабатываем:** всё новое пилим в «Лиге». В «Квартал» переносим только то,
что владелец назвал ЯВНО, с пометкой «изменить в Квартале».

**Причина:** «Лига» — стройка: экраны появляются, ломаются и переделываются каждый день.
Всё, что туда попадает, по определению недоделано. Если такая сборка окажется у человека
и будет ходить на прод, он получит сломанное приложение поверх боевых данных и не поймёт,
что это не «Квартал». Директива владельца от 30.08.2026: «Лига — тестовое приложение, мы
его активно будем разрабатывать, пилить, изменять, добавлять, удалять, и оно должно
находиться локально; Квартал — боевое, на проде».

**Что уже соблюдается и трогать не надо:**
- `android-release.yml` собирает и публикует ТОЛЬКО `mata_kvartal` и только вручную;
  «Лиги» в раздаче тестировщикам (S3, `mata-club.ru/app.html`) нет и быть не должно;
- канал обновлений `app/liga/version.json` существует в коде, но не публикуется.

**Чего это решение НЕ означает.** Backend остаётся ОДИН на всю экосистему (D-12), и `main`
автодеплоится на прод. Поэтому серверные части «Лиги» — `/v1/league`, `/v1/trails`,
`/v1/runner/profile`, `/v1/workouts` — физически лежат на проде. Владелец решил оставить
как есть (30.08.2026): ручки аддитивные, без приложения «Лиги» их никто не зовёт,
«Квартал», Store и сайт про них не знают, а откат означал бы обратные миграции на живой
базе рядом с баллами — риск выше пользы. Правило «локально» относится к ПРИЛОЖЕНИЮ.
Если понадобится жёсткое разделение и на сервере, вводим его флагом на новое, а не
вычищая уже влитое.

**Грабля, из-за которой это записано:** 30.08.2026 сессия собрала «Лигу» командой
`flutter build apk --release` без `--dart-define` и поставила на телефон. Такая сборка
по умолчанию смотрит на `api.mata-club.ru`. Правильная команда для «Лиги» —
`flutter build apk --debug` (или `flutter run`), плюс `adb reverse tcp:8000 tcp:8000`.

**Статус:** активно с 30.08.2026 (директива владельца).

## D-60 — Тропы: сервер сверяет трек и забывает его через 14 дней

**Решение:** телефон присылает прорежённый трек забега; сервер сверяет его с тропами
района, сохраняет РЕЗУЛЬТАТЫ попыток (тропа, время входа, длительность), а сам трек
удаляет через 14 дней. В настройках — выключатель «участвовать в тропах»: выключен,
трек не уходит на сервер вовсе.

**Контекст:** сервер осознанно не хранил GPS-треки (приватность, LAUNCH_READINESS §2),
но тропу без сверки трека честно не засчитать. Владелец выбрал этот вариант из трёх
(`docs/LEAGUE_PLAN.md` §4): «сверяет телефон» — накрутить попытку может любой, клиенту
верить нельзя; «сервер хранит треки» — мы начинаем держать карту передвижений людей.

**Почему 14 дней:** это окно, за которое приходит и разбирается жалоба на накрутку.
Дальше трек — просто маршрут человека, и хранить его незачем. Удаляет задача по
расписанию (`trails.cleanup_tracks`, ежедневно в 3:50).

**Что это значит на практике:**
- маршрут человека появляется на сервере только если он не выключил тропы;
- удаляется автоматически, попытки при этом остаются — стираем маршрут, а не результат;
- в админке видно количество треков на проверке, но не их содержимое.

**Геометрия троп — не в PostGIS.** PostGIS у нас стоит и держит территории, но там
операции над площадями (объединение, разность). Для тропы нужен другой вопрос —
«прошёл ли трек по этой линии», а это сравнение расстояний, которое честнее считать
явно и проверять тестами. Линия лежит списком точек, поиск «троп рядом» — по рамке
обычными числами. Если троп станет много и отбор по рамке перестанет справляться,
перенесём в PostGIS — данные для этого готовы.

**Статус:** активно с 29.08.2026.

## D-59 — «Лига» — отдельное приложение, «Квартал» остаётся стабильным

**Решение:** перестройка геймификации под «свою лигу» (`docs/LEAGUE_PLAN.md`) идёт в
ОТДЕЛЬНОМ приложении `mata_liga/` — копии «Квартала» от 29.08.2026. «Квартал»
(`mata_kvartal/`) продолжает жить своей жизнью: исправления, устранение багов, обновления
для тестировщиков. Разные идентификаторы (`ru.mata.liga` против `ru.mata.kvartal`), разные
имена на экране, свой канал обновлений — приложения ставятся на телефон одновременно.

**Причина:** лига — работа на месяцы, а «Квартал» уже раздан тестировщикам. Вести обе линии
в одном приложении значит месяцами держать людей на недоделанном продукте и смешивать
«сломалось из-за бага» с «так задумано, но ещё не доделано». Владелец: «приложение Квартала
должно существовать отдельно, и к нему будут выходить фиксы, а тестировщики будут тестировать
на нём».

**Следствия:**
- правки между приложениями НЕ переносятся сами — только осознанно, руками;
- backend и контракты API общие: ломать их нельзя ни из «Лиги», ни из «Квартала»;
- CI проверяет оба (`Flutter · kvartal-app` и `Flutter · liga-app`);
- когда лига докажет себя, решаем отдельно: заменяет ли она «Квартал» или остаётся вторым
  продуктом. Сейчас этот вопрос НЕ решаем.

**Статус:** активно с 29.08.2026.

## D-58 — Релиз-поезд: тестерам одно обновление в конце дня, не на каждый фикс

**Контекст:** каждый мерж в main авто-собирал и публиковал APK → тестеры получали много
обновлений в день (много скачиваний по 15–45 МБ, внутренний build-счётчик рос быстро).
Владелец: так делают все крупные — копят правки и выпускают одним релизом.

**Решение:** мерж в main ≠ релиз.
- Правки в течение дня вливаются в main; CI (`ci.yml`/`ios-build.yml`) их проверяет, но
  тестерам НЕ публикует.
- Релиз APK (`android-release.yml`) — только вручную (`workflow_dispatch`, выбор приложений),
  обычно раз в конце дня → накопленные правки уезжают ОДНИМ обновлением.
- **versionName** (человеческая, `0.2.0`) бампается раз в релиз — её видит тестер.
  **versionCode** (build = число коммитов) растёт внутренне, тестер его не видит.

**Причина:** меньше скачиваний, осмысленная человеческая версия, стандарт индустрии
(continuous integration в main + периодический релиз-поезд). iOS/TestFlight — тем же
принципом (заливаем по готовности к релизу, не на каждый мерж).

**Статус:** внедрено (`android-release.yml` — только ручной запуск).

## D-57 — Контент правится ТОЛЬКО в боевом Конструкторе; локальный — среда разработки

**Решение.** Правка контента сайта и приложения (тексты, фото, фоны, порядок блоков)
делается исключительно в боевом Конструкторе `https://api.mata-club.ru/admin/merch/`.
В локальной копии кнопка «Опубликовать» **выключена**: локальная среда нужна разработке —
проверять правки кода до выката, — и не должна выглядеть как второе рабочее место владельца.

**Почему.** Владелец правил «Философию» в локальном Конструкторе и не понимал, почему на
сайте ничего не меняется: интерфейсы одинаковые, адрес в браузере не читают, а публикация
уходила в локальную базу. Час работы ушёл в никуда (локально 129 ключей контента, на
проде — 24). Метки среды как напоминания недостаточно — выключена сама кнопка.

**Почему не убрали локальную среду совсем** (владелец предлагал). Она нужна мне: правки
кода Конструктора и сайта проверяются на ней до выката. Пример того же дня — фикс
позиционирования надписей переписывался трижды, первые две версии не работали; на боевом
это были бы три сломанные версии сайта подряд у живых посетителей. Плюс локальный цикл
«правка → проверка» — секунды против двух минут автодеплоя, и тестовые данные не оседают
в боевой базе.

**Порядок работы:** правки кода → проверка локально → PR → зелёный CI → мерж в main →
автодеплой на прод (~2 мин). Правки контента → сразу в боевом Конструкторе.

**Обходной ключ для разработки:** `?dev-publish=1` в адресе локального Конструктора —
включает публикацию локально, когда нужно проверить сам механизм публикации.

## D-56 — Версионирование: SemVer (versionName) + build-счётчик; до запуска 0.x

**Контекст:** тестер видел «ту же версию» после фиксов — бампался только внутренний
versionCode (число коммитов), а человеческая versionName (`0.1.0`) не менялась.

**Решение:** две независимые метки.
- **versionName** (видит человек) — **семантическая** `МАЖОР.МИНОР.ПАТЧ`: ПАТЧ — фиксы,
  МИНОР — новая функция/экран, МАЖОР — веха. **До публичного релиза оба приложения в
  `0.x`** (бета); на выходе в сторы → `1.0.0`. Бампается ВРУЧНУЮ в `pubspec.yaml`
  (`version:`) по смыслу изменения при каждом релизе.
- **versionCode / build** — целое, `git rev-list --count`, растёт каждую сборку; тестер
  не видит, нужен Android для установки «поверх». CI ставит `--build-number`.
- Тестер видит только versionName (страница тестера / баннер обновления).

**Причина:** стандарт индустрии; честный `0.x` до запуска (не `1.0`, пока публично не
вышли); фикс → ПАТЧ, фича → МИНОР. Старт после наведения порядка: Квартал `0.1.1`,
Store `0.1.0` (был `1.0.0`).

**Статус:** внедрено.

## D-55 — Раздача тест-сборок: самхостинг для Android, TestFlight для iOS

**Контекст:** нужна раздача приложений тест-группе (~10 человек) так, чтобы фиксы легко
доходили и легко обновлялись. Уточнение владельца: ~80% тестеров на iPhone, ~20% на Android.

**Решение:** два раздельных канала по платформам.
- **Android (самхостинг):** постоянный release-keystore → CI собирает подписанный APK при пуше
  в main → S3 (`mata-media/app/<app>/`, публично) + `version.json`. Страница `mata-club.ru/app.html`
  (скачать/версии/QR) + баннер обновления в приложении (сверка `version.json`). Без Google Play.
- **iOS (TestFlight):** sideload на iOS невозможен — только TestFlight. Требует Apple Developer
  Program ($99/год, аккаунт владельца) + сборку на macOS (GitHub Actions macOS-раннер, бесплатно
  для публичного репо) + подпись. Пайплайн ставим после получения Apple-аккаунта.

**Причина:** самхостинг надёжен в РФ (без Google, тестерам не нужны аккаунты, фиксы доходят
мгновенно), CI бесплатен. iOS иначе никак — правило Apple. versionCode = число коммитов
(монотонно, одинаково в сборке и `version.json`). Ключ подписи постоянный (иначе не обновить
«поверх») и забэкаплен трижды (локально/GitHub Secrets/Lockbox).

**Статус:** Android внедрён и вживую (PR #519–#522). iOS — ждёт Apple Developer владельца.

## D-54 — Превью приложения в Конструкторе на проде — через S3

**Контекст:** вкладка «Приложение» в Конструкторе (`/admin/merch/`) грузит web-сборку
`mata_store` в рамке телефона. На проде не работала (`APP_PREVIEW_URL` не задан → localhost).
Собранная web-версия — статика; класть её в git нельзя (публичный репо, артефакты пухнут).

**Решение:** CI (`app-preview.yml`) при изменениях `mata_store` в main собирает `flutter build
web` (флаги: `CONSOLE_EDIT=1` мост правки, `PREVIEW=1` черновики, прод-API, `--base-href
/mata-app-preview/`, `--no-web-resources-cdn`, `--pwa-strategy=none`) и зеркалит в S3
(`mata-media/mata-app-preview/`, публично) через `tools/upload_app_preview.py`. Бэкенд:
`APP_PREVIEW_URL` → origin бакета, добавлен в `DJANGO_CORS_ORIGINS`, ACAO на `/media/`.

**Причина:** чистый репо (сборка в S3, не в git), HTTPS из коробки, авто-обновление превью
при правках кода. Правки КОНТЕНТА и так live (приложение тянет из API). Ключ S3 — в secrets
GitHub. Хостинг — S3 напрямую (virtual-hosted origin), т.к. Конструктор сверяет origin превью.

**Статус:** внедрено (PR #495, #497), проверено вживую.

## D-51 — Прод durability: постоянный диск для БД + S3 (медиа/бэкапы) + Lockbox для секретов

**Контекст:** прод-стек жил на одной ВМ; медиа, БД и бэкапы — на boot-диске (autoDelete) →
терялись при пересоздании ВМ. Реальных юзеров ещё нет, но до запуска пользователей это риск.
Managed-Postgres дорог; владелец следит за расходами.

**Решение (самый дешёвый durable-вариант, ~+200 ₽/мес за диск):**
- **БД** — на отдельном постоянном диске (`network-ssd`, autoDelete=false), bind-mount
  `/mnt/data/pgdata`; cloud-init монтирует и форматирует ТОЛЬКО пустой диск.
- **Медиа** — Yandex Object Storage бакет `mata-media` (публичное чтение), django-storages (D-31).
- **Бэкапы** — ежедневно, шифрованные, в ПРИВАТНЫЙ бакет `mata-club-backups`.
- **Секреты** — Yandex Lockbox (`mata-prod-secrets`), ВМ читает через привязанный SA `mata-vm`.
  `POSTGRES_PASSWORD`/`SECRET_KEY`/`JWT_SECRET` — СТАБИЛЬНЫЕ (иначе постоянная БД не пустит web).
- **TLS** — серт LE на постоянном диске (переиспользуется, не перевыпускается); при исчерпании
  лимита LE — доп. SAN `<IP>.nip.io`; запасной CA ZeroSSL (EAB в Lockbox). Детали — PITFALLS.

**Причина:** ничего не теряется при пересоздании ВМ; секреты вне репо/метаданных; минимальная цена.

**Статус:** ✅ сделано и проверено (2026-08-24): БД пережила ~6 пересозданий, бэкап шифрован в
приватном бакете, HTTPS восстановлен. Follow-up на масштаб: managed-Postgres/реплики.

## D-49 — Второй фактор вместо привязки админки к IP

**Контекст:** механизм из D-48 (белый список IP) заработал, но владелец задал вопрос
раньше, чем вписал адрес: «я планирую сидеть вообще без VPN, у домашнего провайдера
динамический IP — насколько это нам вообще нужно». Вопрос по делу: у нас один
администратор и один вход, а список IP предполагает стабильный адрес.

**Решение:** привязку к IP **убрать полностью** (код, настройки, тесты, пример `.env`),
вместо неё — **второй шаг входа по коду** из приложения-аутентификатора.

- Страницу входа не трогаем: она остаётся прежней («Console Login»). Код спрашивается
  **после** верного пароля, на отдельной странице `/admin/2fa/` в том же оформлении.
- Второй шаг требуется, **только если устройство уже подключено**. Иначе первый же
  администратор на свежем сервере запер бы себя снаружи. Кто не подключил — виден
  в `check_launch_readiness` как незащищённый, это пункт к запуску, а не блокировка.
- Подключение — `python manage.py admin_2fa <логин>`: QR прямо в терминале плюс десять
  одноразовых запасных кодов на случай потери телефона (`--reset` — новые, `--off` — снять).
- После неудачной попытки django-otp сам делает паузу и отклоняет даже верный код —
  на странице это отдельный текст «Слишком много попыток, подождите N с», иначе владелец
  решил бы, что сломался код.

**Причина:** привязка к IP надёжнее ровно там, где адрес постоянный. У динамического
домашнего адреса выбор плохой в обе стороны: вписать сегодняшний — завтра не войти самому;
вписать подсеть провайдера — это уже пол-города, то есть защиты почти нет. Код из приложения
работает с любого адреса, из поездки и с телефона, и защищает даже при утёкшем пароле —
то самое, ради чего затевался белый список.

**Что осталось от D-48:** проверка «не остался ли у суперпользователя пароль из известных» —
она полезна сама по себе и никуда не делась.

**Статус:** ✅ сделано (2026-08-22), 8 тестов + живая проверка всего входа на dev.
**Владельцу остаётся** один раз выполнить `admin_2fa admin`, отсканировать QR и сохранить
запасные коды отдельно от телефона.

## D-48 — Админка закрывается по IP переменной окружения
**Контекст:** пункт «пароль админки + ограничение `/admin/` по IP» висел в списке к владельцу
пять раз. Половина уже закрыта: дефолтный пароль сменён (PR #375, проверка это подтверждает).
Осталось ограничение доступа, и его можно было сделать кодом заранее, а не оставлять
инструкцией к развёртыванию.
**Решение:**
- **`ADMIN_IP_ALLOWLIST`** — адреса и подсети через запятую. Пусто (dev) — ограничения нет,
  ничего не ломается. Задано — `/admin/` доступна только оттуда.
- **Отдаём 404, а не 403.** Постороннему не нужно подтверждение, что админка здесь есть:
  403 сообщает «угадал адрес, не хватило прав», 404 не сообщает ничего.
- Ограничение живёт **в приложении**, а не только в nginx: работает при любом способе
  развёртывания и не теряется при смене прокси. Мусор в переменной игнорируется, а не роняет
  запуск — опечатка в адресе не должна оставлять экосистему без бэкенда.
- **`check_launch_readiness` видит оба пункта:** ограничен ли доступ по IP и не остался ли у
  кого-то из суперпользователей пароль из известных (те, что ходили по документации).
**Причина:** сильный пароль и лимит попыток защищают форму входа, но не убирают её из
интернета. За админкой возвраты денег, ПДн и публикация контента — дешевле не показывать её
никому, кроме владельца, чем полагаться на то, что в Django-админке никогда не найдут дыру.
**Статус:** ❌ ОТМЕНЕНО решением владельца 2026-08-22 — см. **D-49**. Механизм работал, но
не подходит одному администратору с динамическим домашним IP; код полностью удалён, вместо
него второй фактор. Проверка дефолтных паролей из этой записи сохранена.

## D-46 — Удаление клуба: подтверждение и возврат к базовому экрану
**Контекст:** владелец: «нажимаю удалить клуб — выходит пустой экран, переключаю вкладки, он
всё равно пустой» и «нет запроса на подтверждение».
**Найдено две отдельные вещи.**
- **Подтверждения не было вообще.** Кнопка вызывала `leaveClub()` прямо по нажатию, а для
  владельца-единственного участника это безвозвратно удаляет клуб вместе с обложкой,
  участниками и вызовами. Именно так клуб дважды исчезал во время проверок на устройстве:
  случайного касания хватало.
- **Пустой экран — залипшая прокрутка.** Кнопка удаления внизу длинной страницы, то есть в
  момент нажатия список прокручен далеко вниз. После удаления содержимое становится коротким,
  а позиция прокрутки остаётся прежней: список уходит выше видимой области, закреплённая шапка
  остаётся — экран выглядит пустым. Вернуться нельзя: у короткого списка физика по умолчанию
  отключает прокрутку, и позиция уже не исправляется.
**Решение:**
- Диалог подтверждения, где текст **называет последствие**, а не спрашивает «вы уверены?»:
  для владельца — «Клуб будет удалён вместе с обложкой, участниками и вызовами. Отменить это
  нельзя», для участника — «перестанешь быть участником, вступить снова можно по заявке».
- `AlwaysScrollableScrollPhysics` на экране клуба (заодно чинит pull-to-refresh на коротком
  содержимом) и явный `ScrollController`, который возвращает список в начало, когда клуб
  пропал из состояния.
**Причина:** необратимое действие обязано подтверждаться, а изменение длины страницы —
сопровождаться сбросом прокрутки. Оба правила общие, не про клубы.
**Статус:** ✅ СДЕЛАНО (2026-08-21), проверено на устройстве: после удаления сразу базовый
экран со «Стартами».

## D-45 — Нижняя навигация: семь вкладок сведены к пяти
**Контекст:** правило `bottom-nav-limit` из базы скилла `ui-ux-pro-max` — максимум пять пунктов.

**Причина:** пять пунктов — не эстетика, а размер цели под палец и читаемость подписи. Семь

## D-42 — Квартал переходит на визуальный язык сайта МАТА (светлая база)
**Контекст:** владелец сравнил два макета — цвета сайта против цветов бренд-кита mudreza —
и выбрал **цвета сайта**: вариант mudreza показался тусклым. Приложение было тёмным
(чёрный фон, «электрик-блю» акцент, системный шрифт).
**Решение:**
- **Палитра из `САЙТ МАТА/styles.css` 1:1:** молочный `#F4F1EA`, бумага `#FFFDF8`, холодная
  подложка `#E7EEF0`, графит `#20252B`, чернила `#111317`, вторичный `#6F7278`, акцент
  `#57BCD8` (+ `#167A95` для текста по светлому), лайм `#DFF45F`.
- **Шрифты сайта — Manrope и Unbounded.** В приложении своих шрифтов не было вовсе.
  Вариативные Google Fonts нарезаны в статические начертания (`fontTools`) и урезаны до
  латиницы с кириллицей: **402 КБ вместо 1.7 МБ**. Статика, а не вариативный файл, — чтобы
  обычный `fontWeight` работал во всех виджетах без `fontVariations`.
- **Старые имена цветов оставлены переходными псевдонимами.** На `AppColors.*` завязано
  ~720 мест в 30 файлах; переименовывать всё разом — значит получить один нечитаемый PR.
  Псевдонимы (`bgDark` → `bg` и т.д.) перекрасили приложение сразу, а имена вычистим по мере
  перевода экранов.
- **Цвет экрана запуска отделён от цвета иконки** (`splash_background` vs `launch_background`).
  Иконка остаётся лаймом на графите, заставка стала молочной: иначе при запуске экран прыгал
  с тёмного на светлое.
- **Статусные цвета введены явно** (`success/warning/error`) и ограничены состояниями:
  в палитре сайта нет второго сигнального цвета, а беговое приложение обязано показывать
  «GPS потерян» и «не сохранилось».
**Причина:** приложение должно читаться как продолжение сайта, а не как отдельный продукт.
Перенос делаем не «покрасить фон», а по правилам сайта: скругления 14/22/30, мягкие широкие
тени, кнопка-«таблетка», одна кривая движения `cubic-bezier(.33, 1, .34, 1)`.
**Статус:** ✅ фундамент и основные экраны сделаны (2026-08-20). Проверено на устройстве.
**Осталось:** ночная поверхность (вёрстка та же, меняются 4 цвета); вычистка переходных
псевдонимов; полировка мелочей (жёлтые ссылки на экране бега).
**Поправка (2026-08-21):** здесь стояло «вечерний бег — основной сценарий». Это утверждение
я не проверял: в проекте оно нигде не заявлено, данных о времени пробежек нет (в базе две
записи — 18:36 и 08:25). Довод за ночную тему остаётся, но другой: Якутск на 62° с.ш., в
декабре светло примерно с 10:20 до 15:10, поэтому зимой бег вне рабочего дня почти всегда
проходит в темноте. Это география, а не наблюдение за пользователями — приоритет ночной
темы решает владелец.

## D-41 — Store брендируется «скошенным квадратом», Квартал — знаком; обе формы берутся из вектора
**Контекст:** владелец выбрал для Store не знак-«вертушку», а **«Элемент 1»** — скошенный квадрат
(параллелограмм) из бренд-кита mudreza. Store при этом стоял на стоковом шаблоне Flutter: ни
adaptive-иконки, ни цвета сплэша, экран запуска белый и пустой.
**Решение:**
- **Store — графит `#2A302C` на лайме `#EEEA83`**, Квартал — лайм на графите. Формы разные
  (плотная плашка против тонкой вертушки), фон инверсный — на домашнем экране приложения
  различаются с одного взгляда и остаются одной семьёй.
- Обе формы берём **из вектора**: знак — из `logo/svg/Знак*.svg`, плашку — из общего

  признаку**: полигон, у которого после отбрасывания промежуточных точек на сторонах остаётся
  4 угла, противоположные стороны противонаправлены, а отношение сторон ≈ 1.71 (сверено с
  PNG-экспортом 476×278). Параллелограммов в файле три — два других это длинные полосы
  паттерна с отношением ~4.6.
- **Режим подгонки размера зависит от формы:** знак меряем описанной окружностью, плашку —
  шириной. Окружность вокруг широкой и низкой плашки сделала бы её крошечной.
- Скрипт **дособирает недостающие файлы Android** (adaptive-иконка, `colors.xml`,

  шаблонный. Существующее не трогает — Квартал после пересборки бит в бит прежний.
**Причина:** держать один инструмент на оба приложения дешевле, чем два набора ручных экспортов;
а поиск фигуры по геометрическому признаку не сломается, если студия пересохранит SVG в другом
порядке.
**Статус:** ✅ СДЕЛАНО (2026-08-19). Центрирование по центру масс — как в D-40; проверено числом
(отклонение 0.3 px из 1024) и на устройстве.

## D-40 — Иконки и сплэш приложений собираются скриптом из фирменного знака mudreza
**Контекст:** до этого у Квартала на iOS стояла **стандартная иконка Flutter**, у Store — временная
заглушка «M». Бренд-кит от mudreza приехал 2026-08-18 и лежит локально в `brand/` (папка не
коммитится: репозиторий публичный, см. `brand/README.md`).
**Решение:**
- Иконки и сплэш собирает **`tools/brand/make_app_icons.py`** из `brand/logo/svg/Знак*.svg`, а не
  вручную. Знак в SVG — три многоугольника без кривых, поэтому растрируем сами (PIL +
  суперсэмплинг ×4): не нужен ни ImageMagick, ни cairo (на Windows оба ставятся плохо), а
  результат резче, чем растяжение готового PNG в 2–3 раза. Скрипт коммитится, бренд-кит — нет:
  пересобрать иконки можно в любой момент, исходники наружу не уезжают.
- **Масштаб знака подобран под каждую площадку, а не один на всё:** 0.62 ширины для обычной
  иконки; **0.41 для adaptive-иконки Android** — её холст 108dp, а лаунчер показывает только
  центральные 72dp, и при 0.62 маска срезала бы лучи знака; 0.46 для сплэша (на Android 12+
  иконку обрезает круг).
- **iOS-иконки пишем в RGB без альфы** — App Store отклоняет иконки с прозрачностью.
- Цвет `launch_background` в `colors.xml` меняется тем же запуском: он держит и фон
  adaptive-иконки, и сплэш (в т.ч. `windowSplashScreenBackground` для Android 12+).
- **Квартал — вариант 5:** знак `#EEEA83` (лайм) на `#2A302C` (графит).
**Причина:** иконки — расходник, который переделывают не раз (смена палитры, второй продукт,
Роспатент). Скрипт с параметрами `--bg/--fg` превращает это в одну команду и гарантирует, что
оба приложения собраны из одного исходника одинаково.
**Уточнение (2026-08-19):** центрируем по **центру масс** знака, а размер меряем **описанной
окружностью**. Центрирование по габаритной рамке давало смещение 96 px на иконке 1024 —
рамку растягивает длинный правый луч (см. PITFALLS).
**Статус:** ✅ Квартал сделан (2026-08-19). Store ждёт выбора владельца из 18 сочетаний
(`brand/_preview/icons_all.png`).
**Открытый вопрос:** логотип mudreza — латиница «MATA», а по D-34 имя пишется кириллицей. Для
иконок неважно (там знак без букв), но всплывёт в шапках и на сайте.

## D-39 — Админка: анти-брутфорс входа и короткая сессия; бэкапы шифруются до выгрузки
**Контекст:** четвёртый проход аудита — бэкапы и админка. Нашлось два разрыва.
- **Вход в админку ничем не был прикрыт.** Лимиты из `common/throttling.py` — это DRF-классы,
  они действуют только в DRF-вью. `/admin/login/` — обычная вью Django, перебор пароля был
  возможен без ограничений. За админкой возвраты денег, ПДн и публикация контента, а имя
  первого администратора предсказуемо.
- **Дамп уезжал в бакет открытым.** В нём телефоны, email, адреса и весь реестр баллов.
  Ключ доступа к бакету лежит в `.env` на том же сервере (и по умолчанию совпадает с ключом
  медиа), поэтому компрометация сервера означала чтение всех бэкапов разом.
**Решение:**
- **`common/adminsec.py`** — middleware + сигналы: 10 неудачных попыток с одного IP за 15 минут
  → 429 до конца окна, удачный вход счётчик обнуляет. Окно отсчитывается от ПЕРВОЙ неудачи
  (`cache.add` с TTL), а не продлевается каждой следующей. Счётчик в кэше → в проде это общий
  Redis, лимит работает на всех воркерах сразу (D-07). IP берём из `X-Real-IP`, который ставит
  наш nginx: `REMOTE_ADDR` за прокси равен адресу прокси, и блокировка одного заблокировала бы всех.
- **Сессия админки — 8 часов и `SESSION_EXPIRE_AT_BROWSER_CLOSE`** вместо дефолтных двух недель.
- **`BACKUP_ENCRYPT_PASSPHRASE`** — дамп шифруется локально (`openssl aes-256-cbc`, PBKDF2,
  200 000 итераций) ДО отправки; `restore.sh` расшифровывает на лету, не кладя открытый файл на
  диск. Без пароля поведение прежнее, но скрипт предупреждает. `umask 077` — локальные дампы
  доступны только владельцу.
**Причина:** защита должна стоять там, где ценность, а не только там, где удобно её ставить:
API прикрыли лимитами ещё в P0, а вход в админку — самую привилегированную точку — не прикрыли
ничем. Шифрование бэкапа полезно ровно тем, что пароль хранится ОТДЕЛЬНО от сервера: иначе
второй ключ лежал бы рядом с первым и ничего не добавлял.
**Статус:** ✅ СДЕЛАНО (2026-08-18). Проверка на CI (локально Docker Desktop не поднимался).
Отчёт — `docs/SECURITY_AUDIT.md`. **Осталось владельцу:** задать `BACKUP_ENCRYPT_PASSPHRASE`
и хранить его в менеджере паролей — потеряется пароль, бэкапы станут нечитаемы; завести для
бакета бэкапов ОТДЕЛЬНЫЙ сервисный аккаунт, а не переиспользовать ключ медиа.

## D-38 — Зависимости бэкенда обновляются по известным уязвимостям; Django на ветке 5.2 LTS
**Контекст:** третья строка таблицы аудита — зависимости на известные CVE, раньше не проверялись.
`pip-audit` нашёл **10 уязвимостей в 2 пакетах**: 6 в Django 5.1.15 (CVE-2026-48587, -6873, -8404,
-48588, -53877, -53878) и 4 в sqlparse 0.5.5 (CVE-2026-71491, -59894, -59893, -54284).
Причина не в том, что забыли обновиться, а в верхней границе `Django>=5.0,<5.2` в requirements:
она держала нас на ветке 5.1.x, куда исправления уже не приезжают — обновление «в рамках пина»
их не подтягивало и не могло.
**Решение:**
- `Django>=5.2.16,<6.0` — переход на ветку **5.2 LTS** (там закрыты все шесть; 6.0 не берём,

- `sqlparse>=0.6.0` зафиксирован **явно**, хотя это транзитивная зависимость Django: иначе
  версию выбирает резолвер и уязвимая может вернуться при следующей сборке.
- Верхние границы ставим по мажорной версии (`<6.0`), а не по минорной (`<5.2`): минорный
  потолок — это и есть механизм, который отрезал нас от исправлений.
**Причина:** известные CVE в веб-фреймворке — самый дешёвый для атакующего путь; проверка
`pip-audit` занимает минуту и должна повторяться, а не быть разовой акцией.
**Статус:** ✅ СДЕЛАНО (2026-08-18). Проверка — на CI: он ставит зависимости начисто из
requirements и гоняет все 280 тестов, что для бампа версий надёжнее локального контейнера
(локально Docker Desktop в этот момент не поднимался). Отчёт — `docs/SECURITY_AUDIT.md`.
**Дальше:** прогонять `pip-audit` перед каждым релизом; рассмотреть его отдельным шагом CI
(сейчас не добавлен: падение сборки из-за свежей CVE в чужом пакете блокировало бы работу,
решение об этом — за владельцем).

## D-37 — Базовый аудит безопасности: сумма заказа, телефон-логин и тип файла считаются на сервере
**Контекст:** вторая половина launch-gate §13 — базовый аудит безопасности, раньше не проводился.
Проверялись деньги, баллы, ПДн, загрузка файлов и аутентификация.
**Найдено три места, где сервер верил клиенту:**
- **Сумма заказа (критично).** `total` брался из тела запроса; по нему выставлялся счёт в
  ЮKassa и начислялись баллы. Корзину на 50 000 ₽ можно было оформить с `total: 1`.
- **Телефон.** Менялся через `PATCH /profile` без подтверждения, а вход по SMS ищет аккаунт
  именно по номеру, и поле не уникально → присвоение чужого номера и перехват входа.
- **Тип файла.** Определялся по `Content-Type` и расширению из имени — оба присылает клиент →
  `x.html` в media и хранимый XSS на домене медиа.
**Решение:** все три величины вычисляет сервер.
- `orders/pricing.py`: минимум суммы = товары по ценам каталога минус РЕАЛЬНО списанные баллы

**Причина:** любые значения, влияющие на деньги, доступ и хранимый контент, должны вычисляться
на сервере — клиент их только предлагает. Отчёт: `docs/SECURITY_AUDIT.md`.
**Статус:** ✅ СДЕЛАНО (2026-08-18). 280 тестов зелёные (13 новых). Владельцу остаётся: сменить
пароль админки и ограничить `/admin/` по IP, добавить `nosniff` на раздачу `/media/` в nginx.
Отложено: уникальность телефона в БД (нужна миграция с проверкой дублей), ротация JWT.

## D-36 — Rate-limit по назначению эндпоинта: витринное чтение отдельным щедрым scope
**Контекст:** нагрузочный прогон (§13 launch-gate) показал, что анонимные эндпоинты каталога
получают 429 на ~98% запросов. Причина не в величине числа, а в модели: один общий потолок
(120/мин на IP) применялся и к дешёвому публичному чтению, и к чувствительным операциям.
Каталог смотрят БЕЗ входа, а мобильные операторы РФ раздают абонентов через CGNAT — сотни
человек за одним публичным IP; один просмотр каталога это 10–20 запросов. То есть 6–10
одновременных гостей «одного оператора» уже видели пустой магазин.
**Рассмотрены три варианта:** (1) поднять общий `anon` — отодвигает порог, но ослабляет защиту
для ВСЕГО анонимного, включая перебор; (2) развести лимиты по назначению эндпоинта;
(3) ключевать по IP + идентификатор устройства — точнее всех, но заголовок шлёт клиент, значит
обходится рандомизацией и даёт ложное чувство защиты + требует правок во всех клиентах.
**Решение — вариант 2:**
- Новый scope **`public` = 3000/мин на IP** для витринного чтения: каталог, поиск, товар,
  бренды/размеры, баннеры, контент сайта, юр-документы, отзывы на чтение. Арифметика: активный
  гость делает 30–60 запросов/мин → 50–100 одновременных гостей за одним IP оператора; при этом
  50 rps вдесятеро ниже измеренной пропускной способности (581 rps), то есть лимит сохраняет
  смысл как защита от перегруза.
- **`PublicReadThrottle` считает только безопасные методы.** На смешанных URL (отзывы к товару —
  GET и POST) запись в щедрый scope не попадает: для неё есть `WriteUserJWTRateThrottle` /
  `WriteAnonIPRateThrottle`, которые наоборот пропускают чтение.
- **Вход не ослаблен: `auth` остаётся 20/мин** — анти-брутфорс кода из SMS не трогаем.
- Базовый `anon` поднят 120 → 300/мин (прочие гостевые сценарии, напр. товар по ссылке).
**Причина:** строгость лимита должна соответствовать цене и чувствительности запроса, а не быть
компромиссом между несовместимыми задачами. От скрейпинга витрины throttle не защищает в принципе
(обходится сменой адреса) — там работают кэш и CDN (D-31); а брутфорс входа защиты требует.
**Статус:** ✅ СДЕЛАНО (2026-08-18). 267 тестов зелёные, из них 4 новых: 150 подряд чтений каталога
проходят без 429 (прежний лимит резал на 121-м), вход по-прежнему упирается в 20/мин, и оба
направления фильтрации по методу. Прогон: доля успешных чтений витрины 2% → 69% при том же
синтетическом давлении (остаток 429 — артефакт теста: он бьёт с ОДНОГО IP на ~155 rps, чего
реальный оператор не создаёт).

## D-33 — Оплата ЮKassa реализована; баллы за покупку привязаны к подтверждению платежа
**Контекст:** аудит готовности к запуску (2026-08-14) показал, что «каркас оплаты» —
пустая заглушка: `create()` возвращал `confirmationUrl: ""` даже с ключами, а документация
утверждала «активируется ключами». Владелец прошёл бы модерацию ЮKassa, вставил ключи и
обнаружил бы отсутствие оплаты только на живом заказе. Рядом вскрылась вторая проблема:
баллы начислялись при **создании** заказа — с реальной оплатой это дыра (набрать баллов
и не заплатить), а баллы = деньги.
**Решение:**
- **Реальный ЮKassa API v3** (`orders/payment.py`): создание платежа, `fetch_payment`
  (авторитетный статус), `create_refund`. HTTP на `urllib` — HTTP-клиента в зависимостях
  бэкенда нет, ради трёх запросов пакет не тянем (тот же приём, что в `accounts/sms.py`).
- **Ключ идемпотентности детерминирован** от (заказ + сумма): повтор «Оплатить» возвращает
  тот же платёж, а не создаёт второй → покупателя нельзя списать дважды.
- **Вебхук `POST /v1/payments/webhook`** — эндпоинт публичный, тело ЮKassa не подписывает,
  поэтому телу не верим: берём из него только id платежа и **перезапрашиваем статус по API**
  своими ключами. Подделать «succeeded» и получить товар бесплатно нельзя (есть тест).
- **Баллы — только по подтверждённой оплате** (`orders/awards.py`, идемпотентно по заказу):
  при выключенном провайдере (dev/CI) начисляем при создании заказа, как раньше; при
  включённом — по вебхуку. Отмена платежа возвращает списанные баллы.
- **Ошибка провайдера = 502**, а не молчаливый «pending»: заказ не помечается оплаченным.
- Возврат денег — действие в админке (полный возврат + возврат списанных баллов).
**Причина:** деньги и баллы требуют идемпотентности и авторитетной проверки на сервере;
доверять телу неподписанного вебхука нельзя; расхождение документации с кодом опаснее
отсутствия функции — оно создаёт ложную уверенность при запуске.
**Статус:** ✅ СДЕЛАНО (2026-08-14). 259 тестов зелёные. Владельцу остаётся: аккаунт ЮKassa,
ключи в прод-`.env`, адрес вебхука в личном кабинете. Пуши закрыты отдельно — D-35.

## D-35 — RuStore Push реализован; мёртвые токены устройств удаляются автоматически
**Контекст:** вторая заглушка из того же аудита: `notifications/push.py` возвращал `False`
всегда — пуши не ушли бы никогда, даже с ключами. Плюс вопрос, что делать с токенами
устройств, на которых приложение удалили: они копятся в `device_tokens` вечно.
**Решение:**
- **RuStore Push (VK PNS)**: `POST https://vkpns.rustore.ru/v1/projects/{id}/messages:send`,
  `Authorization: Bearer <сервисный токен>`. Нужны **два** значения — `RUSTORE_PROJECT_ID`
  и `RUSTORE_PUSH_KEY` (адрес отправки содержит проект, одного ключа мало); проверка
  готовности в `check_launch_readiness` требует оба.
- **Ответ `NOT_FOUND` → токен удаляется** (`DeadToken`): устройство отвалилось навсегда,
  иначе на каждое уведомление тратится впустую HTTP-запрос, и таблица пухнет.
- **Прочие ошибки провайдера токен НЕ трогают** и не роняют поток: лента уведомлений
  внутри приложения важнее доставки на телефон (тест это фиксирует).
- FCM не вводим (D-24): `FCM_SERVER_KEY` убран из проверки готовности как несуществующий путь.
**Причина:** тот же принцип, что и в D-33 — интеграция считается готовой только с реальным
вызовом; данные, которые заведомо мертвы, чистятся автоматически, а не «когда-нибудь руками».
**Статус:** ✅ СДЕЛАНО (2026-08-14). Владельцу остаётся: аккаунт RuStore → Push-уведомления →
Проекты → взять Project ID и сервисный токен в прод-`.env`.

## D-32 — Наблюдаемость ошибок: GlitchTip (self-host в РФ), не строим свою вкладку
**Контекст:** в проде будут накапливаться ошибки (особенно передача данных телефон↔бэк). Нужна «видимость»: ловить, группировать по корню, фильтровать по устройству/версии/платформе, чинить причину. Владелец спросил, как это устроено у техно-лидеров и что взять нам.
**Изучено (Sentry / Firebase Crashlytics / Datadog):** «вкладка ошибок» — зрелый класс продуктов. Ядро у всех: группировка событий по КОРНЮ (fingerprint/стек-трейс) → одна карточка с частотой × числом юзеров; фасеты (версия/устройство/ОС/окружение/теги); карточка (стек-трейс + breadcrumbs + контекст устройства + затронуто юзеров); стадии (For Review→Reviewed→Resolved→Ignored + авто-reopen регрессии); алерты (new/regression/**velocity-spike**); release health (crash-free %). AI-путь к корню — Sentry Seer Autofix (находит корень, передаёт фикс внешнему агенту, включая **Claude Code**).
**Решение:** НЕ строим вкладку ошибок в Django-админке с нуля (это переизобретение Sentry). Берём **GlitchTip** — Sentry-совместимый (те же SDK/DSN, код не меняем), на нашем стеке (Django+Celery+Postgres+Redis), 512 МБ–2 ГБ вместо 16 ГБ/40 контейнеров у полного Sentry. **Self-host на Yandex Cloud → дата-резиденция РФ** (152-ФЗ). В нашу админку — только сводка-виджет + ссылка. **Роль «AI, чинящего корень» — Claude** (разбирает топ ошибок → фикс + тест). Апгрейд на полный Sentry+Seer (авто-передача фикса в Claude Code) — позже, когда объём оправдает.
**Причина:** дёшево + РФ-резиденция + наш стек + вся нужная видимость; не тратим недели на переизобретение зрелого продукта. Каркас Sentry на бэке уже вшит (`SENTRY_DSN`) — GlitchTip заведётся сменой одной переменной.
**Статус:** ✅ метод утверждён (2026-07-06); внедрение предстоит («приступим в скором времени»). Полный план и структура — `docs/OBSERVABILITY.md`. Автономно Claude может начать с этапов 2/3/4/6 (обогатить бэк-Sentry, каркас в приложениях, плитка в админке, ранбук) до поднятия GlitchTip владельцем.

## D-31 — Медиа-хранилище: S3/Object Storage для прода, локальный диск в dev
**Контекст:** аватары, фото отзывов, баннеры и лого/обложки клубов грузятся через `default_storage` и лежат в локальном docker-томе `/srv/media`. Для прода это не годится: файлы должны быть в объектном хранилище с CDN (переживать пересборку, масштабироваться, отдаваться быстро). Нужен прод-бэкенд без слома dev.
**Решение:** тот же паттерн graceful degradation, что у SMS/оплаты/пуша — включается переменными окружения:
- **`common/media.py:media_storages(env)`** возвращает Django-настройку `STORAGES`: при заданных `MEDIA_S3_BUCKET` + `MEDIA_S3_ACCESS_KEY` + `MEDIA_S3_SECRET_KEY` → `storages.backends.s3.S3Storage` (Yandex Object Storage, S3-совместимый; endpoint/region/CDN-домен настраиваемы; `public-read`, без querystring-подписи); иначе → локальный `FileSystemStorage`. Частичные ключи → безопасный откат на локальный.
- **URL загрузок строятся через `default_storage.url(saved)`** (не хардкод `/media/…`) → в dev остаётся `/media/…`, в проде — S3/CDN. Заменено во всех точках загрузки (аватар, фото отзыва, лого/обложка клуба). ImageField'ы (товары/категории/баннеры/контент) и так S3-готовы через `.image.url`.
- `django-storages[boto3]` в requirements; **импортируется ЛЕНИВО** (только при активном S3) — dev/CI без ключей его не трогают. Статус виден в `check_launch_readiness` (инфра → «Медиа-хранилище»).
**Причина:** объектное хранилище + CDN — требование прод-инфры (D-01/§1 launch); env-переключение не ломает dev/CI; единый способ включения, как у прочих интеграций. Бандл-фото товаров (`/media/products/…`, примонтированы в dev) — отдельная миграция данных, вне этого решения.
**Статус:** ✅ СДЕЛАНО (2026-07-04). Смоук: S3Storage инстанцируется, URL с CDN-доменом корректен. Осталось владельцу: создать бакет + сервисный аккаунт Yandex, вписать `MEDIA_S3_*` в прод-`.env`.

## D-30 — Продуктовая аналитика: единый поток событий + ретеншн по когортам
**Контекст:** нужна событийная аналитика и удержание — понимать активацию/удержание пользователей экосистемы. Раньше был только админ-дашборд метрик, без потока событий и когортного анализа.
**Решение:** отдельное приложение `analytics` с единой лентой событий на всю экосистему (SSO → один user_id):
- **Модель `Event`** (`analytics_events`): user_id, name, source (kvartal/store/site/server), props(JSON), created_at. Индексы по user_id, name, (name, created_at).
- **`track(name, user_id, source, **props)`** — server-side запись в ключевых местах (регистрация/вход, завершённый забег, покупка, захват территории). **БЕЗОПАСНО:** событие — факт, а не деньги; любой сбой записи глотается, чтобы не ломать основной поток.
- **`POST /v1/events`** — клиентские события (экраны/клики), батч до 100; привязка к uid из токена; клиент не может выдать источник за `server`.
- **Ретеншн (`analytics.retention.weekly_cohorts`)** — когорты по неделе регистрации × активность (сигнал активности = транзакция баллов в неделю; работает и ретроспективно, до накопления событий). Команда `analytics_retention --weeks N`.
**Причина:** отдельный модуль не засоряет доменные; безопасный `track` = аналитика не может уронить бизнес-поток; ретеншн на существующем сигнале (баллы) даёт пользу сразу, события копятся для более богатого анализа позже. Админ-дашборд/виджеты аналитики — за параллельным чатом (админку ведёт он), поэтому пока команда + endpoint + функция.
**Статус:** ✅ СДЕЛАНО (2026-07-04). Дальше: события → виджеты в админ-дашборде (когда возьмётся админка), воронки, отправка в внешнюю BI (по решению владельца).

## D-29 — Кэш тяжёлых агрегатов: TTL для глобальных, инвалидация для пер-юзерных
**Контекст:** после D-07 (Redis/Celery) появился общий кэш. Тяжёлые агрегаты (лейдерборд users/clubs/districts — Sum по всем транзакциям + имена/клубы + PostGIS; `/me/stats` — забеги/баллы/заказы) считались в БД на каждый запрос. Под нагрузкой это узкое место.
**Решение:** кэшируем через общий кэш Django (`common/cache.py`), но с РАЗНОЙ стратегией по природе данных:
- **Лейдерборд — короткий TTL (60с), без пер-write инвалидации.** Это горячий ГЛОБАЛЬНЫЙ агрегат: меняется от действий любого юзера, поэтому инвалидация на общем ключе = постоянный пересчёт/стемпид. Кэшируем юзеро-НЕзависимую часть (ранжированный список + имена/клубы), а `isMe`/`me` считаем на запрос из закэшированного. Рейтинг терпит секунды устаревания.
- **`/me/stats` и `/loyalty/account` — кэш по uid + явная инвалидация.** Агрегаты на юзера (read-only показ); `add_txn` вызывает `invalidate_user(uid)` (сбрасывает статистику + карточку лояльности) → свои данные свежие сразу после своего действия (забег/покупка/захват/трата идут через add_txn). Плюс safety-TTL (120с) на изменения мимо add_txn (напр. флаг-забег без очков).
- **АВТОРИТЕТНЫЕ проверки — мимо кэша.** `redeem` («хватает ли баллов») и `before` в `add_txn` читают СЫРОЙ `balance_of`, не кэш: иначе по устаревшему балансу можно уйти в минус / списать лишнее. Кэшируем ТОЛЬКО показ, не бизнес-решения.
**Причина:** правильный тип кэша под тип данных: глобальный горячий ключ — TTL (ограниченный пересчёт), пер-юзерный — точечная инвалидация (свежесть там, где юзер её ждёт), авторитетные деньги-решения — всегда из БД. Работает и на Redis (прод/стек), и на LocMem (dev-без-Redis) — код одинаков.
**Статус:** ✅ СДЕЛАНО (2026-07-04). Строится на D-07. Дашборд админки в кэш пока НЕ трогаем (его ведёт параллельный чат).

## D-28 — Бюджетная стартовая конфигурация Yandex Cloud для валидации гипотезы (+ триггер масштабирования)
**Контекст:** D-17 выбрал Yandex Cloud как кандидата, но без конкретики по железу и цене. Стратегия владельца: **дёшево подтвердить гипотезу спроса → масштабироваться только после подтверждения**. Изучили цены Яндекса (2026), нужна минимальная стартовая конфигурация и ориентир по стоимости (в рублях, для ИП — D-18).
**Решение — этап валидации (минимальный бюджет):**
- На сервере крутится **только бэкенд** (приложения — на телефонах; карта/погода — с клиента). Поэтому платим за **ОДНУ VM**, где в Docker всё сразу: Django+Gunicorn, **PostgreSQL/PostGIS** (образ `postgis/postgis`), Redis, Celery, Nginx+HTTPS (+ Sentry self-host по D-25 — туда же или рядом).
- **Конфиг:** 2 vCPU (50% доля), 4 ГБ RAM, ~30 ГБ SSD — **≈ 2 000–2 500 ₽/мес**. + Object Storage (S3) для медиа — десятки ₽/мес. Трафик в пределах **бесплатных 100 ГБ/мес**. **Бэкапы с 1-го дня:** снапшот диска + `pg_dump` в Object Storage (launch-gate §13).

## D-23 — Начисление баллов — серверно-авторитетное (анти-чит S-04); клиент очки за бег не присылает
**Контекст:** баллы экосистемы = реальная ценность (тратятся в Store). Но ВСЕ начисления считал и слал КЛИЕНТ через `POST /loyalty/transactions` с произвольным `amount`: Квартал — `runnerRun` (км×10) и `runnerTerritory` (+50); Store — `purchase` (сумма/10) и `registration`. Любой мог подделать запрос и намайнить баллы → бесплатные товары. Это дыра №1 (S-04).
**Решение:** **начисления (earn) считает только сервер; клиент их не присылает.** Трата (`redeem`) уже была серверно-авторитетной. Переход по фазам, чтобы не ломать живые потоки:
- **Phase 1 (сделано): бег.** `POST /v1/runs` сам валидирует забег (скорость ≤ 40 км/ч — как в territories; дистанция/время; суточный лимит 150 км) и начисляет `runnerRun = км×10`, идемпотентно по `runId`. Неправдоподобный забег → сохраняется `flagged` + причина, **0 очков** (видно в админке для модерации, S-10). `POST /loyalty/transactions` с `source=runnerRun` → **403**. Клиент Квартала перестал слать `runnerRun`; баланс обновляет после синка забега. Клиентская офлайн-очередь баллов теперь **выбрасывает** навсегда-отклонённые (4xx), а не зацикливает их.
- **Phase 2 (✅ сделано):** `runnerTerritory` начисляется в `POST /v1/territories/capture` (+50, идемпотентно по `captureId`, после серверной валидации геометрии); `purchase` (сумма ÷ 10) и `registration` (+50 за первый заказ) — в `POST /v1/orders` (только при создании, идемпотентно по `orderId`). Все три добавлены в `_SERVER_ONLY_SOURCES` → 403 для клиента. Клиенты (Квартал run/territory, Store checkout) перестали минтить и обновляют баланс после события.
**Причина:** очки = деньги → их размер обязан считать сервер по проверенным данным, а не доверять клиенту. Пороги переиспользуют логику territories (единый потолок скорости). Сырой GPS по-прежнему не покидает устройство (приватность §2) — сервер судит по сводке (дистанция/время), не по треку.
**Подводные камни:** (1) флаги — консервативные (рубим только явный спуфинг: >40 км/ч, >100 км/забег, >150 км/сутки), чтобы не наказывать честных; борд-лайн — позже риск-скоринг (S-04 полный); (2) суммарный анти-чит начисления за покупку (Store) — пока клиентский, закрыть в Phase 2; (3) забеги-`flagged` хранятся для разбора/обжалования (журнал решений сервера — часть S-04).
**Статус:** ✅ Phase 1 + Phase 2 реализованы и проверены (Django test Client). Phase 1: валидный забег +50, дубль без задвоения, чит-скорость/дистанция → flag/0, клиентский runnerRun → 403, purchase не сломан. Phase 2: захват → +50 серверно (дубль без задвоения), первый заказ 1000₽ → +100 purchase +50 registration, второй заказ → +50 без рег-бонуса, клиентские runnerTerritory/purchase/registration → 403. **Все начисления теперь серверные.** Дальше (полный S-04): риск-скоринг (мульти-аккаунт, режимы доверия), обжалование флагов. Связано с D-02, D-09/D-14, D-20 (морозный коэффициент ляжет в серверный расчёт за бег), S-04, S-10.

## D-21 — Шрифты SportStore встроены локально (Inter/Oswald в assets), без обращения к Google
**Контекст:** магазин грузил шрифты через `google_fonts` **по сети** (`fonts.gstatic.com`) при первом запуске: зависимость от стороннего CDN, на офлайн/без доступа к Google — fallback на системный шрифт (другой вид), плюс приватность (запрос к Google = утечка IP). У Квартала `google_fonts` стоял в зависимостях, но **нигде не использовался** (мёртвая зависимость).
**Решение:**
- **SportStore:** скачали те же 10 файлов, что `google_fonts` тянет с gstatic (**Inter** w400–900, **Oswald** w400–700), положили в `assets/fonts/`, включили `GoogleFonts.config.allowRuntimeFetching = false`. Пакет сам берёт их из ассетов (проверяет ассеты **до** сети; при отсутствии точного веса — ближайший в семействе). Файлы **байт-в-байт** идентичны сетевым (sha256 == имя файла на gstatic) → **вид не меняется** (совместимо с D-01).
- **Квартал:** убрали неиспользуемую зависимость `google_fonts`.
**Причина:** офлайн-устойчивость + приватность (§2: не шлём IP в Google) + детерминированный вид без сетевых сюрпризов; не нарушает D-01, т.к. шрифты те же.
**Важно на будущее:** добавишь в магазине новый вес/семейство через `GoogleFonts.*` — **положи соответствующий `.ttf` в `assets/fonts/`** (иначе с `allowRuntimeFetching=false` текст молча упадёт на системный шрифт).

## D-20 — Погода: реальная (MET Norway, с клиента); морозный коэффициент к баллам — отдельно, отложен
**Контекст:** чип погоды показывал зашитые фейковые «−24°C ×1.4». Тут смешались две РАЗНЫЕ вещи: (а) отображение погоды и (б) морозный множитель очков («система баллов»). Фейк вводил игрока в заблуждение.
**Решение — РАЗДЕЛИЛИ:**
- **Погода (отображение) — реализована по-настоящему.** Источник — **MET Norway** (`api.met.no`): бесплатно, без ключа, коммерция разрешена (CC-BY), и **реально доступен из РФ**; зовём **напрямую с клиента → бэкенд НЕ нужен** (обязателен User-Agent с контактом; прокси через свой backend — опция на будущее, §12 launch). Чип = реальная температура + иконка состояния; **тап → мини-окно** с деталями: ветер (скорость + направление), вероятность осадков, влажность, ощущается-как (ветрохолодовой индекс). Модуль `features/weather/` (provider + view). _Open-Meteo отклонён: из РФ не грузился (соединение висло, чип «…») + бесплатный тариф только non-commercial — та же ловушка, что платные карты в D-19._
- **Морозный коэффициент к БАЛЛАМ (множитель ×) — остаётся ОТЛОЖЕННЫМ** (это часть экономики баллов, не погоды). Кривую владелец **выбрал — «Средняя»**, чтобы потом не выбирать заново: ≥0°C ×1.0; −10 ×1.1; −20 ×1.25; −30 ×1.4; −40 ×1.6; ≤−45 ×1.8 (потолок). Реализация позже: серверный расчёт по кривой + очки = `км×10×коэф`. Общий серверный анти-чит всего начисления (сейчас сумма считается на клиенте) — отдельная, более широкая задача.
**Причина:** погоду честно показать сразу (не врать фейком); коэффициент трогает общую с магазином экономику баллов → отдельно и осторожнее. Погода с клиента = ноль работы в бэкенде → не пересекаемся с параллельной работой в `territories`.
**Статус:** ✅ погода реализована и **проверена на устройстве** (реальные 18°C, MET Norway). Источник переведён Open-Meteo→**MET Norway** (Open-Meteo недоступен из РФ); также починен баг (provider вис на GPS-стриме → брали неблокирующий снимок позиции). ## D-19 — Карта: тайл-провайдер OpenFreeMap (НЕ западные платные), attribution обязателен

**Статус:** ✅ внедрено (2026-06-21). Квартал: `vector_map_tiles` + стиль **Bright** (`https://tiles.openfreemap.org/styles/bright`), attribution на карте (OpenFreeMap/OpenMapTiles/OSM). Онлайн — вектор Bright; офлайн (скачанный город) — растровый кэш-фолбэк; пока стиль грузится — растр CARTO. Проверено на устройстве. **Launch-gate:** при росте — self-host того же стека (D-17).

## D-16 — Сглаживание GPS-трека: фильтр Калмана в приложении (не snap-to-road)
**Контекст:** сырой GPS «дрожит» (±3-10 м даже при хорошей точности) — линия маршрута и зелёная метка прыгают. Рассматривали: (A) сглаживание в приложении (Калман) + анимация метки; (B) привязка к дорогам (snap-to-road, OSRM/Mapbox); (C) гибрид (A в забеге, B в истории).
**Решение:** A — лёгкий фильтр Калмана (`features/run/data/gps_kalman.dart`) сглаживает позицию (вес фикса = его точность), линию и метку рисуем по сглаженной точке; метка анимированно «скользит» между фиксами. Сырой фикс по-прежнему отсекается по точности/скорости/прыжку до Калмана.
**Причина:** Квартал — игра про территории: захват территории идёт по *реальному* пути (двор/парк/срезка; полигон маршрута, НЕ гексы — см. D-09). Snap-to-road «притянул» бы трек к дороге → исказил захват и античит, плюс требует внешний сервис. Калман даёт и гладкую линию, и честный путь, офлайн и бесплатно. Snap-to-road — возможно позже только как «красивая картинка» готовой пробежки в истории.
**Статус:** A внедрён. Параметр процесса q≈3 м/с; при необходимости подстроить по полевым тестам.

## D-14 — Модель территорий: гибрид (живой слой с распадом + вечный личный след)
**Контекст:** обсуждали, держать ли жёсткое 72ч-удержание или сделать вечную фиксацию (твоё/навсегда, перехват всегда).
Чистая «вечная» убивает ядро бегового приложения (нет повода бегать повторно, особенно пока мало игроков),
насыщает карту и растит геометрию без предела. Чистый распад 72ч — слишком наказывает за паузу (отток).
**Решение (выбор владельца):** ГИБРИД из двух слоёв:
- **Живой слой** (карта/рейтинг/клубы): территория держится **7 дней** (`HOLD_HOURS=168`) от последнего забега,
  перехват бегом — всегда; не подтвердил забегом → освобождается. Держит карту живой и мотивирует бегать.
- **Вечный личный след** (`footprints`): объединение всего, что когда-либо пробежал — растёт, НЕ уменьшается
  (ни временем, ни перехватом). Показывается в профиле как «исследовано N км²». Даёт чувство «моё навсегда»
  без насыщения соревновательной карты.
**Причина:** баланс мотивации бегать (выгодно нам) и удержания/эмоции владения; новичкам всегда есть место.
**Статус:** активно. Бэк: `territories` (живой, 7д) + `footprints` (вечный) + `GET /v1/footprint`. Клиент: карточка профиля.
**Защита свежего захвата (внедрено 2026-06-21, выбор владельца — Вариант Б):** кусок, захваченный
за последние `PROTECT_HOURS=24`, нельзя перехватить. Реализовано через таблицу `recent_captures`
(куски + время); при перехвате срезается только незащищённое: `effective = контур − чужие защищённые
куски моложе 24ч`. Свой свежий кусок защищён, через 24ч стареет и снова контестабелен. Проверено
(API): защищённый владелец не теряет площадь, после истечения — теряет. Окна (7д/24ч) подкрутим по тесту.

## D-11 — Рейтинг по КМ (не по баллам), периоды неделя/месяц
**Контекст:** по чему ранжировать рейтинг.

## D-09 — Модель территорий «Квартал»: по реальному маршруту, НЕ гексы
**Контекст:** как захватывать и отображать территории и при этом тянуть 1000–3000 игроков без тормозов.
**Решение:** территория = площадь ВНУТРИ реального бегового маршрута игрока (произвольный полигон),
тематически — настоящие районы/кварталы. **H3-гексы ОТКЛОНЕНЫ** (ломают суть и вид «Квартала»).
Заранее заготовленные блоки из `zones.json` как единица владения тоже уходят.
- **Отрисовка:** полупрозрачная заливка цветом владельца + насыщенный контур; карта (дома/улицы) видна
  насквозь. Цвета: свои / клуб / чужие / свободно. Точный оттенок и прозрачность — дизайн, пока не утверждаем.
- **Захват:** замкнул петлю → область внутри = территория. Возвращаться в точку старта НЕ обязательно:
  маршрут, начавшийся на своей территории и снова вошедший в неё, замыкается о собственную границу
  (касание в 2 точках A/B), новый кусок прирастает (`ST_Union`). Полная отдельная петля вне своей
  территории = новая отдельная территория.
- **Перехват чужого:** пересечение с чужой территорией отрезается у врага и переходит игроку (`ST_Difference`).
- **Чистка/сглаживание при фиксации (сервер, один раз):** выкинуть мусорные точки и GPS-прыжки →
  упростить (Дуглас–Пекер) → скруглить углы (Chaikin/сплайн) → проверить геометрию (без самопересечений).
  Форма остаётся реальным маршрутом; сила сглаживания тюнится.
- **Производительность:** хранить точный контур, на отдалённом зуме отдавать упрощённо; грузить только
  видимую область (bbox + zoom); кэш; реалтайм-дельты — позже.
- **Источник правды — сервер:** владение, пересечения, срок удержания 72 ч, античит (скорость ≤ 40 км/ч,
  адекватность GPS). Клиент рисует оптимистично, затем сверяется с сервером.
- **Геометрия — PostGIS** (`ST_Union` / `ST_Difference` / `ST_Simplify*` / `ST_MakeValid`).
- **Текущее расхождение (переделать):** карта берёт зоны со старого Go-бэка `localhost:3000` и красит
  заготовленные блоки; владение лежит локально (SharedPreferences). Зерно нужной модели уже есть —
  `CapturedArea` хранит полигон реального маршрута.
**Причина:** «Квартал» = захват реальных районов по своему бегу; гексы ломают суть и красоту.
Нужна плавность при 1000–3000 игроках без багов.
**Статус:** принято (2026-06-14), реализация поэтапно вместе с переходом на Django/PostGIS (D-06).

## D-07 — Docker — нужен, но позже и поэтапно
**Решение:** Docker Compose для локальной инфраструктуры (Django, PostgreSQL/PostGIS, Redis, Celery worker/beat)
вводим ПОСЛЕ старта Django, не на первом шаге. Порядок: GitHub/монорепо → Django scaffold → Postgres/PostGIS → Docker → Redis/Celery.
**Причина:** консистентное окружение для обоих агентов и деплоя; но не блокировать текущие шаги. (Решение Codex.)
**Статус:** ✅ СДЕЛАНО (2026-07-04). Docker Compose: `db` (PostGIS) + `redis` + `web` (Django) + `worker` (Celery)
+ `beat` (расписание). Celery-приложение `config/celery.py`, конфиг из settings (namespace `CELERY_*`),
брокер/бэкенд — `REDIS_URL` (тот же, что и кэш). **Graceful degradation:** без брокера (нет `REDIS_URL`/
`CELERY_BROKER_URL`) — режим `CELERY_TASK_ALWAYS_EAGER`: задачи выполняются синхронно inline, отдельная инфра
не нужна (dev/CI/тесты работают как раньше). Первые задачи: `notifications.send_push` (async-пуш, не блокирует
HTTP-ответ) и `territories.cleanup_expired_territories` (beat — ежедневная чистка протухших зон/защит в 03:30).
